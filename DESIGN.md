# Canopy — Design

A language-agnostic REPL frontend for the terminal, in Haskell. Canopy runs an existing REPL (ghci,
python, node, julia, utop, …) as a child process behind a pseudo-terminal and puts a modern editing
and display layer over it: tree-sitter for syntax, LSP for semantics, the REPL itself for runtime
facts, and [libghostty-vt](https://github.com/ghostty-org/ghostty) as the terminal emulator that
interprets everything the child prints.

This document is the architecture: what to build, in what order, with which boundaries, and how each
piece is tested. There is no code yet. When code exists and the two disagree, this document is the
intent and the code is behind. The repository conventions are taken from `../cassini` on purpose,
so that neither project re-argues them (§2).

where the design must not foreclose it. Jupyter kernels in particular are a plausible second

trigger.

## 1. Architecture

### 1.1 The central decision: canopy is a terminal emulator with one pane

Most REPL frontends either *replace* the REPL's line editor from inside the language (ptpython,
bpython, IPython, PyREPL, utop, rebel-readline) or *wrap* the child as a dumb line-oriented pipe
(rlwrap, Emacs comint, ghcitty). The first is not language-agnostic. The second cannot cope with what
REPLs actually print: colours, cursor motion, progress bars, `\r` overwrites, clear-screen, pagers,
and full-screen programs launched from the REPL.

Canopy takes a third position: **it is a terminal emulator for the child and a terminal application
for the host**, the way tmux or zellij is, specialised to a single REPL pane. Every byte the child
writes goes into a libghostty-vt `Terminal` (§4), so canopy always knows the child's screen exactly,
in cells, with styles, hyperlinks, semantic-prompt marks and scrollback. Canopy then composes its own
frame — child output, its editor, menus, hints, diagnostics — and draws that frame to the host.

Consequences, each of which the rest of the document depends on:

- **Output is structured, not scraped.** A block's output is a range of child-terminal rows, which
  can be reformatted as plain text, VT or HTML by libghostty's formatter, searched, folded, copied
  and exported (§8.4).
- **The child's queries are answered correctly.** Device attributes, XTVERSION, colour-scheme and
  size queries are answered by the child terminal, not forwarded to a host that never saw them.
- **Full-screen children work.** When the child enters the alternate screen, canopy passes host input
  through, re-encoded by libghostty's key and mouse encoders according to the modes *the child* set
  (§8.6).
- **The host is decoupled.** Canopy's rendering to the host is its own problem (`tendril`, §5.6); the
  child never writes to the host directly.

### 1.2 Three sources of knowledge, one input

Canopy's intelligence comes from three places, with different costs and different blind spots:

| Source | Knows | Blind to | Latency |
| :--- | :--- | :--- | :--- |
| **tree-sitter** (§9.1) | Syntax of the input, incrementally, per keystroke; completeness; structure | Meaning | Sub-millisecond |
| **LSP** (§9.2) | Static semantics: types, scopes, imports, diagnostics, documentation | Runtime state of the session | Tens–hundreds of ms |
| **the REPL** (§9.3) | Runtime state: bindings created by evaluation, loaded modules, actual types | Anything before it is evaluated; costs a round trip to a possibly busy child | Unbounded; unavailable while busy |

Neither LSP nor the REPL is sufficient alone, and the design's job is to merge them (§9.4). The
**shadow document** (§9.2) is the bridge in one direction: it is how the language server learns about
the session. **Introspection writes back** in the other: types the REPL reports for runtime bindings
are projected into the shadow document as declarations, so the server can type-check uses of them.

### 1.3 Packages, and the dependency rule

```
                       canopy  (app: profiles, child, grammar store, LSP, event loop)
                  /       |        \
   ghostty-effectful   tendril   tree-sitter-effectful
          |           (line editor)          |
   ghostty-vt-ffi                     tree-sitter-ffi
          |                                  |
   libghostty-vt (C, pkg-config)     tree-sitter runtime (C, vendored)

                    canopy-prelude  ← every package
```

- **`tendril` does not depend on `ghostty-effectful` or on tree-sitter.** It is a general line editor
  and must be usable over a plain terminal without a Zig-built C library. Its *test suite* depends on
  `ghostty-effectful`, which serves as an oracle for rendering and input decoding (§11.2). That edge
  is test-only, and §2.6 enforces it.
- **`ghostty-effectful` and `tree-sitter-effectful` know nothing about REPLs**, nor about each other.
  They are general high-level bindings.
- **Only `canopy` sees all three.** The adapters — ghostty cells to tendril cells (§8.3), tendril
  edits to tree-sitter edits and tree-sitter spans to tendril highlights (§9.1) — live there.

### 1.4 The shape of computation: one owner, many feeders

Canopy's core is an **Elm-style state machine** owned by one thread:

```haskell
update :: Event -> Model -> (Model, [Command])
```

Feeder threads — the child PTY reader, the host input reader, each language server's reader, timers,
the file watcher — do nothing but turn bytes into `Event`s and push them onto one bounded STM queue.
`Command`s are interpreted by effect handlers. This is what makes the core testable as a pure
function (§11.4), it serialises access to the libghostty handles, which are not thread-safe (§4.6),
and it gives one place where stale asynchronous results are discarded (§6.4).

### 2.1 Packages

A root `cabal.project` lists seven packages, each in a directory of its own name:

| Package | Holds | Depends on (beyond prelude) |
| :--- | :--- | :--- |
| `canopy-prelude` | `Canopy.Prelude`: relude minus collisions (§2.3) | `relude` |
| `ghostty-vt-ffi` | `Ghostty.FFI.*`: raw bindings, `hsc2hs` layouts, the layout test | `libghostty-vt` via pkg-config |
| `ghostty-effectful` | `Ghostty.Effectful.*`: the `effectful` interface | `ghostty-vt-ffi`, `effectful-core` |
| `tendril` | `Tendril.*`: the line editor, plus `tendril-demo` | `effectful-core`, `text`, `text-rope`, `unix` |
| `tree-sitter-ffi` | `TreeSitter.FFI.*`: raw bindings, the vendored runtime, generated by-value shims | none; the C is vendored |
| `tree-sitter-effectful` | `TreeSitter.*`: the high-level interface, grammar loading, typed kinds (Template Haskell), queries and predicates | `tree-sitter-ffi`, `effectful-core`, `bytestring`, `unix`, `aeson` (TH-time only), `template-haskell` |
| `canopy` | `Canopy.*`: the library, the `canopy` executable, the suites | all of the above, `effectful`, `lsp-types`, `toml-parser`, `fsnotify` |

**Why split there.** As in cassini (its D7), the trigger is dependency divergence. A user of the line
editor should not need Zig or libghostty; a user of either binding should not pay for `lsp-types`
and its `lens` tree, or for the other binding's C library. Each FFI is its own package so that its
C API's churn is quarantined: when libghostty-vt's API changes (§14.1), `ghostty-vt-ffi` changes and
`ghostty-effectful`'s *types* usually do not; when the vendored tree-sitter is bumped, the shims are
regenerated in `tree-sitter-ffi` (§5A.2) and `tree-sitter-effectful` follows only where semantics
moved.

The LSP client stays inside `canopy` for now. D-deferred-1 holds the trigger for splitting it out.

### 2.3 The prelude

`canopy-prelude` is cassini-prelude's design, copied: relude through `mixins`, with the fifteen
mtl names that collide with `Effectful.State.Static.Local` and `Effectful.Reader.Static` subtracted
once, plus the transformer vocabulary. Every consuming stanza carries:

```cabal
  build-depends:    base, canopy-prelude, ...
  mixins:
    base hiding (Prelude),
    canopy-prelude (Canopy.Prelude as Prelude)
```

Canopy-specific subtractions:

- **No subtraction is needed for `optics`.** A module under relude-as-`Prelude` (through the same
  mixins) that does an unqualified `import Optics` and uses `&`, `_1` and `.~` compiles without
  ambiguity (checked, relude 1.2.2.2, optics 0.4.2.1): relude's `(&)` is `Data.Function`'s, the same
  entity `optics` re-exports. If a later relude or optics adds a real collision, it is subtracted
  here, not hidden per module.
- `Text` is the string type; `ByteString` for every byte stream (PTY, LSP transport, VT). `String`
  only where a dependency demands it.
- No partial functions; no `unsafePerformIO`. The unsafety audit is a `grep` (§10.6).

D-deferred-2: whether the published libraries keep depending on `canopy-prelude`.

### 2.6 Layering, enforced

The rules, by module name across all packages:

1. **`Ghostty.FFI.**` is private to `Ghostty.Effectful.**`** (and `Test.Ghostty.**`). Nothing in canopy
   sees a raw pointer.
2. **`Ghostty.Effectful.**` is not imported by `Tendril.**`** — only by `Canopy.**`, `Test.**` and
   `Bench.**`. This is the test-only oracle edge of §1.3.
3. **`Canopy.Ffi.**`** is private: `Canopy.Ffi.Pty` (the PTY shim, §6.2) to `Canopy.Child.Pty`.
4. **The pure core does not do IO.** `Canopy.App.Model`, `.Update`, `.Event`, `.Command` may not
   import `Canopy.Child.**`, `Canopy.Lsp.Transport`, `Canopy.Syntax.GrammarStore`,
   `TreeSitter.Parse`, or any `Effectful.Concurrent.**`. It sees those subsystems only through their
   pure model modules. (It *may* import `TreeSitter.Tree`, `.Node` and `.Query`: their reads are pure
   functions, §5B.2, and the model holds the current input's `Tree`.) The allow-list does not include
   `Main`: every executable's and test suite's `Main` has that one name, so lint trusts it with
   nothing, and canopy's `Main` reaches these only through `Canopy.Cli` and `Canopy.App.Run`.
5. **`TreeSitter.FFI.**` is private to `TreeSitter.**`** (and `Test.TreeSitter.**`), as rule 1 does for
   ghostty. Nothing in canopy sees a `TSNode` or a raw pointer. `TreeSitter.Internal.Pure` (§5B.2) is
   private to `TreeSitter.**`.
6. **`Language.LSP.Protocol.Lens` is imported only qualified, `as L`,** and only by `Canopy.Lsp.**`
   and `Canopy.Intel.**`. Its unqualified names (`range`, `label`, `uri`, …) would shadow canopy's
   own, and outside the LSP modules there is nothing for it to name. hlint's `modules:` restriction
   carries `as: L`. Each use goes through optics' `lensVL` (§2.7); the type checker, not lint,
   enforces that.
7. **`Control.Lens.**` is banned everywhere.** The house uses optics (§2.7). A rule with an empty
   `within`.

### 2.7 House style

- **`effectful`, never an mtl stack or `ReaderT Env IO`.** Libraries use `effectful-core`; the
  application uses `effectful` (for `Concurrent`, `Process`, `FileSystem`). Each subsystem is a
  dynamically dispatched effect with at least two interpreters — a real one and a pure or scripted
  one — which is what the test plan stands on (§11). Operations are generated with `effectful-th`'s
  `makeEffect`. `Ghostty` is the exception: static, with one interpreter (§4.2).
- **`optics`, never `lens`.** Records get labels with `makeFieldLabelsNoPrefix`; external types that
  derive `Generic` get labels for free through `optics-core`'s generic-label instances. `lsp-types`'
  generated records all derive `Generic` (`deriving stock (Show, Eq, Ord, Generic)`), but their fields
  carry its `lens`-era underscore prefix, so the labels are `#_label`, `#_textEdit`, and record dot
  reads `ci._label` (checked: both compile and work against `lsp-types` 2.4.0.0 under GHC 9.12.4).
  **Simple protocol fields always use the underscore labels**: `r & #_start % #_line %~ (+ 1)` to
  update, and record dot (`ci._label`) to read. A simple field is a field of a concrete
  `lsp-types` record.
  **`lsp-types`' own lenses, converted with optics' `lensVL`, are for what labels cannot say
  clearly.** In practice that means code written once for every protocol type that has a field, e.g.
  `shiftRange :: L.HasRange s Range => UInt -> s -> s` using `lensVL L.range`, over `Diagnostic`,
  `TextEdit`, `Location` and the rest. A `lensVL L.x` on a concrete record, where `#_x` would do, is
  a review finding. `lensVL` itself is required, not just conventional: a bare `L.label` given to an
  optics operator is a type error ("Couldn't match expected type: Optic … with actual type:
  (a1 -> f0 a1) -> s0 -> f0 s0"). So `lens`'s operators never get in, even though `lsp-types`
  brings the package into the build (checked, optics-core 0.4.2.1, lsp-types 2.4.0.0: `lensVL`
  lenses compose with `%` and with labels, `.~` and `%~` work through them, and the `shiftRange`
  example compiles and runs).
  Inline anonymous types in the protocol are `row-types` records with no `Generic`; the few canopy
  touches are read through `Canopy.Lsp.Rows`, the one module that imports `Data.Row`. **Reading uses record
  dot; updating uses optics**: `m.editor.buffer` to read, `m & #editor % #buffer .~ b` to write.
  Prisms for sum types (`#_Busy`), affine traversals for "the selected completion, if any".
  `Canopy.Optics` provides the effectful state operators (`use`, `.=`, `%=`, `zoomMaybe`) over
  `Effectful.State.Static.Local`, since `Optics.State` is mtl-shaped.
- Explicit export lists everywhere; `Internal` modules hold representations and their siblings the
  API.
- No partial functions; indexing returns `Maybe` or `Either`.
- Haddock on every export, with a 100% floor checked by `scripts/check-haddock.py` (cassini's).

## 3. `ghostty-vt-ffi` — the low-level binding

### 3.1 Getting the library

libghostty-vt is released on its own, with its own version numbers, as a signed source tarball and a
**deps tarball** holding every Zig package the build needs (`release.files.ghostty.org/libghostty-vt/<V>/`,
minisign-signed, with a signed `SHA256SUMS`). `zig build` in the source tarball builds the library
(its `LIB_VERSION` file selects it; no `-Demit-lib-vt`) and produces a shared library, a static
library (`libghostty-vt.a`), headers and pkg-config files. It has no dependencies, not even libc.
Distribution packages do not exist yet, so:

- **The release is pinned** in `ghostty-vt-ffi/LIBGHOSTTY_VT_VERSION` (`1.0.0`), as tree-sitter's is
  in `TREE_SITTER_VERSION` (D14, M1.11). Upgrading is one deliberate commit that changes the pin and
  the two tarballs' sums, regenerates the generated binding (§3.3), and says why. The layout test
  (§3.4) and the coverage check then name whatever the new headers changed. (Until M1.11 the pin
  was a commit, `GHOSTTY_COMMIT`, built from a git checkout.)
- **`scripts/build-libghostty.sh`** downloads both tarballs of the pinned release, checks each
  against the sha256 pinned in the script (as it does Zig's), and builds offline with
  `zig build --system <deps> -Doptimize=ReleaseFast` into `_deps/ghostty/<version>/`, printing the
  `PKG_CONFIG_PATH` and `LD_LIBRARY_PATH` to export. A `cabal.project.local` is never required. Each
  build uses a new, empty `ZIG_GLOBAL_CACHE_DIR`: upstream's packaging guide says a Zig 0.17 cache
  holding a package archive can crash a `--system` build with "reached unreachable code". The
  pinned sums were checked against upstream's minisign key when the pin moved; the script checks
  the signature too when `minisign` is installed, but the pinned sum is the required check. Nothing
  is fetched by Zig, so the curl prefetch M0 needed (Zig 0.17.1's fetcher failed with
  `TlsInitializationFailed` against `deps.files.ghostty.org`) is gone with the git build.
- **`--release` builds for the baseline CPU** (`-Dcpu=baseline`, into
  `_deps/ghostty/<version>-baseline/`), as upstream's packaging guide recommends for distribution
  (D17). The default build targets the build machine's CPU, which is right for development; but the
  shipped `canopy` links the library statically (below), and a native build would die with `SIGILL`
  on an older CPU. The release job uses `--release`.
- **Zig 0.17.x.** Each libghostty-vt release requires one Zig minor version (`minimum_zig_version`
  in `build.zig.zon`; 1.0 requires 0.17); the script uses a `zig` 0.17.x on `PATH`, or downloads
  Zig 0.17.1 and checks its sum.
- **The package declares `pkgconfig-depends: libghostty-vt ==1.0.0`**, exactly the pin (D15).
  cabal resolves the constraint against the pkg-config database, so a missing or wrong library
  fails at *configure* time, not link time and never at run time. (Checked with cabal 3.16.1.0: `==`
  on a pkg-config version parses and is enforced, and a range below the installed version is
  rejected at planning; the wildcard form `==0.1.*` is *not* accepted in `pkgconfig-depends` — it is
  a parse error.)
- **A `static` flag** (default on for the release build, off for development) switches the dependency
  to the separate `libghostty-vt-static` pkg-config package that the build also installs, so the
  shipped `canopy` binary has no runtime library dependency. Zero transitive dependencies is what
  makes this cheap.

### 3.2 What the API looks like

Transcribed from the pinned headers (`include/ghostty/vt/*.h`), because the binding's shape follows
from it:

- **Opaque handles** created by `ghostty_*_new(allocator, &out, …)` and released by `ghostty_*_free`:
  `GhosttyTerminal`, `GhosttyRenderState` and its row and cell iterators, `GhosttyFormatter`,
  `GhosttyKeyEncoder`, `GhosttyKeyEvent`, `GhosttyMouseEncoder`, `GhosttyMouseEvent`,
  `GhosttyOscParser`, `GhosttySgrParser`, `GhosttySearch`, `GhosttySnapshotDecoder`, selection
  gestures, tracked grid refs.
- **Every fallible call returns `GhosttyResult`**, setters included: `SUCCESS`, `OUT_OF_MEMORY`,
  `INVALID_VALUE`, `OUT_OF_SPACE`, `NO_VALUE`, `IO_ERROR`, `LIMIT_EXCEEDED`, `REJECTED`, and
  `UNSUPPORTED` for a key this library does not know or a feature compiled out of it
  (`-Dvt-features`). A null handle or out pointer is `INVALID_VALUE` or a no-op, never a crash.
- **Keyed getters and setters**: `ghostty_terminal_get(t, GhosttyTerminalData key, void *out)`,
  `ghostty_terminal_set(t, GhosttyTerminalOption key, const void *value)`, and the same shape for
  render state, rows, cells, the formatter (`ghostty_formatter_set`/`_get`), the encoders, search,
  kitty graphics. The type of `out` depends on `key` and is documented on each key. **Every key enum
  starts with `INVALID = 0`**, which no binding maps. A setter given a null value **restores the
  option's default** (as a new handle has it), so where "none" differs from the default the header
  names another value: no scrollback byte limit is `SIZE_MAX`, its default is 10,000 bytes
  (regression 11).
- **Sized structs** carry a leading `size` field initialised by `GHOSTTY_INIT_SIZED(T)` (or
  `ghostty_sized_init`), so the library can accept structs from older headers: at least the struct's
  first released size, and never nested, in an array or by value. 13 are sized at 1.0 (the encoder
  geometry, paste, the render state's cursor, colours and row selection, the selection options, the
  write stop, memory usage, and the two clipboard replies). Others are **frozen**, with no `size`
  and a fixed layout, zeroed with `{0}`: `GhosttyGridRef`, `GhosttySelection`, `GhosttyStyle` (16
  bytes: three colours and a `GhosttyStyleFlags` word with the attributes in bits 0–7 and the
  underline in bits 8–10), and every struct a callback receives.
- **Callbacks** registered as options (`GHOSTTY_TERMINAL_OPT_WRITE_PTY`, `_BELL`, `_TITLE_CHANGED`,
  `_PWD_CHANGED`, `_SEMANTIC_PROMPT`, `_CLIPBOARD_WRITE`, `_RENDER_HOLD`, …), with a `USERDATA`
  pointer. Some are notifications; some answer queries and return values (`_COLOR_SCHEME`,
  `_DEVICE_ATTRIBUTES`, `_ENQUIRY`, `_XTVERSION`, `_SIZE`).
- **Render state is incremental**: `ghostty_render_state_update(state, terminal)`, then a global dirty
  flag and per-row dirty iteration (`row_iterator_next_dirty`), with cells read through iterators
  whose validity ends at the next update.
- **`ghostty_type_json()`** returns a JSON description of every public struct: size, and each field's
  offset, size and type, including tagged unions. This is what §3.4 tests against.
- **The ABI is stable across 1.x** (M1.11): a minor release only adds functions, types, enum values
  or fields at the end of a sized struct, and a behaviour change is a new function, the old one
  marked `GHOSTTY_DEPRECATED`. The shared library's SONAME is `libghostty-vt.so.1` and its symbols
  are versioned (`ghostty_*@@GHOSTTY_VT_1.0`). Upstream's CI holds this with abidiff and goldens.
  The snapshot byte format is outside the promise (§8.7). Before 1.0 the header said the API "is not
  yet stable and is definitely going to change" (§14.1).

### 3.3 Binding conventions

- **`CApiFFI` (`foreign import capi`) for every function**, so that GHC compiles calls against the
  real prototype through the C compiler. `static inline` helpers in the headers
  (`ghostty_mode_new`) are reachable only this way. The C compiler catches less than it seems
  (checked, GHC 9.12.4 and GCC 16): an integer of the wrong width or signedness, as a parameter or a
  result, converts silently and truncates at run time, and a `Ptr` to a Haskell-defined type (every
  struct, and every handle, a newtype over one) reaches C as `void *`, which converts to any
  pointer. Only an integer for a pointer, and a pointer to the wrong C scalar, are errors.
- **So signatures are checked against the headers by name.**
  `scripts/check-ghostty-signatures.py` maps each `capi` import's parameter and result types, each
  callback type's, and each field of every record that marshals a C struct, to C (`Word16` to
  `uint16_t`, `Ptr T` to `T *`, a `Ghostty…` type to the C type of its name) and compares them with
  the pinned headers, ignoring `const`. Enums and handles are compared by name, so one handle for
  another fails; type synonyms and C scalar typedefs resolve to what they name, and each synonym
  must name what its C typedef does.
- **Fifteen functions pass a struct by value** at the pin (thirteen take one, and
  `ghostty_mouse_event_get_position` and `ghostty_key_event_get_utf8` return one), which GHC's FFI
  cannot do. Each that the binding binds gets a `static inline` pointer shim in
  `ghostty-vt-ffi/include/gvtffi_shims.h`, taking the struct by pointer (and returning one through
  an out pointer), called through `capi` like any other function, so the compiler still checks both
  prototypes. The shims are generated from the header prototypes by `scripts/gen-ghostty-ffi.py`,
  one `{{shim}}` line each in that header's template, added as each function is bound (thirteen so
  far; the other two are `snapshot.h`'s, M6.10's). M1.2 wrote its five by hand; M1.3's first half
  more than doubled them, past the point where a hand list was the cheaper check, as tree-sitter's
  56 are generated (§5A.2). (Before 1.0 there were nineteen and seventeen bound; 1.0 moved six to
  pointers or removed them, and its sized-struct rule forbids passing a sized struct by value, so a
  new one will only ever be small and frozen.) A function bound without its shim is a C compile error,
  since `capi` checks the prototype. Two callbacks *return* a struct by value (`ENQUIRY` and
  `XTVERSION` return a `GhosttyString`), and one *receives* structs by value (`io.h`'s
  `GhosttyMimeReaderFn`, given a `GhosttyString` and a `GhosttyWriter`, which paste's MIME reader
  uses), which a Haskell `wrapper` cannot make. Their types are bound, without a `wrapper`, and a
  function of any of them has to be written in C (§4.5); `ghostty-vt-ffi-test`'s paste test has its
  MIME reader in C for that reason, and so does `ghostty-effectful`'s `paste`
  (`cbits/gveff_paste.c`, M1.9).
- **One module per header** (`terminal.h` → `Ghostty.FFI.Terminal`, with its callback half in
  `Ghostty.FFI.Terminal.Callbacks`). A header is bound in part where only part of it is needed yet,
  and the module says which part.
- **The mechanical code is generated from the headers**, by `scripts/gen-ghostty-ffi.py`, and
  committed: each enum's patterns, `Unknown` view and descriptor, each plain struct's record,
  `Storable` instance and descriptor, each callback type and its `wrapper`, the named modes, the
  constants a header spells as `#define`s over a scalar typedef (the `GhosttyMods` and
  `GhosttyKittyKeyFlags` bits, the named palette colours), the by-value pointer shims, and the
  layout test's enum rows. The input is a template per module
  (`ghostty-vt-ffi/gen/**.in`, and one for the shim header), the module as written by hand with
  directive lines where generated code goes; tagged unions, arrays, handles and imports stay
  hand-written there. Docs are the header's own. CI runs it with `--check`, so a pin
  bump that changes a header cannot leave the binding behind, and an edit to generated code cannot
  survive.
- **Coverage is checked against the headers.** `scripts/check-ghostty-coverage.py` lists every
  `GHOSTTY_API` function and every type the pinned headers declare, and fails on one that is neither
  bound nor listed in `ghostty-vt-ffi/coverage.txt` with the PLAN.md step that binds it (or `never`,
  with a reason). An entry that no longer defers anything fails too. The signature check cannot
  find a function nobody bound; this can.
- **A tagged union is a Haskell sum**: one constructor per arm the binding names, plus an `…Other`
  constructor that carries a tag the binding does not name, whose value it cannot read. The
  `Storable` instance reads the arm the tag selects. A union whose arms all have one type
  (`GhosttyPoint`) is a record. C `bool` is `CBool`, never `Bool`, whose `Storable` is four bytes.
- **The binding never supplies an allocator.** Every function that takes a `GhosttyAllocator *` is
  passed null, the library's default, and the struct is not marshalled. A Haskell allocator would
  run Haskell inside every allocation the library makes, against §4.1's third goal.
- **`hsc2hs` for every struct and enum.** Offsets, sizes and enum values come from the headers through
  the C compiler, never from hand-copied numbers.
- **Enums are newtypes over the C integer with pattern synonyms**, `COMPLETE`-annotated, plus an
  `Unknown` view. C enums are open (`GHOSTTY_ENUM_MAX_VALUE` padding exists to allow growth), so a
  closed Haskell sum here would turn a library upgrade into undefined behaviour. The high level
  (§4) closes them, and a value outside the closed set is the thrown `UnknownEnum` (§4.7), not a
  constructor: the version check (§3.4) makes the linked library the pinned one, and the layout
  test makes the binding name every value the pinned one has, so no caller could meet it. (M1.5;
  this sentence first read "with an explicit unknown case". `ResultCode` keeps its unknown case,
  because it is what `Invariant` carries, not what an operation returns.)
- **`unsafe` FFI calls by default**, `safe` only for calls that can call back into Haskell
  (`vt_write`, `vt_write_until`, `paste`, `render_state_update` if it ever gains callbacks). This is
  a per-import decision recorded in the import's comment, because an `unsafe` call that re-enters
  Haskell is a crash, and that cannot be checked by the compiler. What is checked is that each
  decision was made against the header as it is: `ghostty-vt-ffi/safety.txt` records every bound
  function's mode and a fingerprint of its doc comment and prototype, and
  `scripts/check-ghostty-safety.py` fails when either drifts, as at a pin bump that changes what a
  function documents, until someone re-reads it and records the result (`--update`). It is a
  prompt to re-read, not a proof; a callback documented only in a header's overview, not on the
  function, does not change the fingerprint. Reading the header found more
  than the writes: `terminal_reset` and `terminal_resize` end a render hold through its callback
  (and resize sends an in-band size report), `continuation_write` calls its writer, and
  `terminal_set` is `safe` because the header does not promise that no option reports through a
  callback. `formatter_format` calls its writer. Some calls are `safe` for a different reason:
  they call nothing back, but can run long, and an `unsafe` call would hold up every Haskell thread
  at the next GC. `terminal_compress` can stall on a full pass, and the formatter's
  `format_buf`/`format_alloc` walk the whole screen including the scrollback (a selection is
  formatted through the formatter since 1.0). Setting and reading a formatter's options is short and
  `unsafe`. `render_state_update` stays `unsafe`: it copies the viewport, not the scrollback, and
  is on the per-frame path. `terminal_paste` is `safe`: it pulls the data through the paste's MIME
  reader and streams the encoding to `WRITE_PTY`. The terminal-free `paste_is_safe` and
  `paste_encode` stay `unsafe`: they call nothing back, and each is one pass over a buffer the
  caller hands over, not a walk of the scrollback. So do the encoders, parsers and widths, which
  are short and, for `osc_next`, per byte.
- **Raw types only.** `Ptr`, `FunPtr`, `CSize`, `Word8`. No `ForeignPtr`, no exceptions, no `Text`.
  Everything that makes it safe is `ghostty-effectful`'s job; this package's job is to be complete and
  exactly right. The one exception is `ghosttyStringBytes`, which copies a borrowed `GhosttyString`
  out as a `ByteString` (a null pointer is empty): bytes, not `Text`, so that `ghostty-effectful` and
  this package's own tests read the C boundary's strings through one function rather than two copies.

### 3.4 The layout test

`ghostty-vt-ffi-test` loads `ghostty_type_json()` from the linked library and compares every struct's
size and every field's offset with the `hsc2hs`-derived values compiled into the binding. They come
from different places — the headers the binding was compiled against, and the library actually
linked — so the test catches a header/library mismatch (a stale `_deps`, a distro `.so` at a
different commit) that would otherwise be silent memory corruption. It also checks that
`ghostty_build_info` reports the pinned build, and that the binding names every enum value the
library has.

The values compiled into the binding are exported beside each type as a descriptor
(`Ghostty.FFI.Layout`: `CStruct`, `CField`, `CEnum`), every number in it from `hsc2hs`, so the test
has no layout of its own and a struct or enum is added to it by one row. For a struct it checks size,
alignment, and each field's offset and size, and that the field *names* are exactly the library's, so
a field the binding does not marshal is a failure too. Each struct row also carries a sample
value: the `Storable` instance's `sizeOf` and `alignment` must equal the descriptor's, and the sample
must `poke` and `peek` back unchanged over zeroed and over all-ones memory, so a field the instance
skips is a failure. For an enum it checks the type's size and, for each value the binding names, that
the manifest has that full C name (its `prefix` plus key) with that value; and, the other way, that
the binding names every value the manifest lists (apart from the `…MAX_VALUE` padding). So the
binding is exhaustive at the pin, and a value a bump adds is a failure rather than an `Unknown` at
run time. The `Unknown` view stays, because C enums are open. `ghostty_type_json()`
describes enums as well as structs, so "exists" is checked against the linked library, not only the
header. Every enum's `Unknown` view (§3.3) is built from its descriptor's values, and each enum row
carries a total match on the `COMPLETE` set; the test checks, over every value the library lists,
that the view excludes exactly the named ones. So a pattern synonym missing from the descriptor fails
the test, and one missing from the match fails to compile. That a bound type has a row at all is
checked by `scripts/check-layout-rows.py` in CI's lint job: every hand-written `Storable` instance
needs a `…Layout` descriptor, every newtype over a C integer an `…Enum` one, and every descriptor a
row.
The identity check (D14, D15, M1.11) has three parts: the linked library's `ghostty_version()` equals
`LIBGHOSTTY_VT_VERSION` exactly (a development build's has a `-dev+…` suffix, so no pre-release or
build metadata passes); the headers' `GHOSTTY_VT_VERSION` equals it too, which catches headers left in
`_deps` from another pin; and build info reports every optional feature (`FEATURE_*`, and
`KITTY_GRAPHICS`, which `-Dvt-features` gates too: regression 12) compiled in,
since a `-Dvt-features` build still reports the release's version but turns the calls of a missing
feature into `UNSUPPORTED`. (Until M1.11 the pin was a commit, stamped into the library's
`VERSION_BUILD` with `-Dlib-version-string`, since a git build reported only `0.1.0-dev`; a release
reports its own version.)

At startup, `ghostty-effectful` performs the same version check once and refuses to run against a different
library (§4.7); this is the one runtime check of the C boundary, and it runs before any handle exists.
It compares the linked version and features with `ghosttyPinnedVersion`, which `gen-ghostty-ffi.py`
writes from `LIBGHOSTTY_VT_VERSION` into `Ghostty.FFI.BuildInfo` (`{{pin}}`), so a pin bump that is
not regenerated fails `--check`. 1.0 makes "same major, minor at least the headers'" memory-safe,
but the check stays exact (D15): §3.3's and §4.7's argument that `UnknownEnum` is unreachable, and
the layout test's exhaustiveness, rest on the exact pin, and a newer 1.x adds enum values. With
static linking for releases the runtime check bites only in development, where exact is right. The
relaxation is D-deferred-11 (§15.2).

## 4. `ghostty-effectful` — the high-level `effectful` binding

### 4.1 Goals

1. **No use-after-free, no double free, no borrowed pointer escaping its scope** — by types, not
   discipline.
2. **`get`/`set` whose result type follows from the key** — by types.
3. **No Haskell code running inside a C callback** beyond appending to a buffer.
4. **Errors are values**, and the impossible ones are not represented.

### 4.2 The effect and scoped handles

```haskell
data Ghostty :: Effect   -- static dispatch; the owner thread and the open-handle count

runGhostty :: IOE :> es => Eff (Ghostty : es) a -> Eff es (Either VersionMismatch a)

-- A terminal lives in a region named by s, like ST.
withTerminal
  :: Ghostty :> es
  => TerminalConfig
  -> (forall s. Terminal s -> Eff es a)
  -> Eff es a
```

`Ghostty` is statically dispatched (`Static WithSideEffects`). Its operations are plain functions in
the module of what they act on (`Ghostty.Effectful.Terminal`, `.Render`, `.Format`, …), each starting
with the owner check (`owned`, through `ownedIO` for one IO call and `scoped` for a handle), so no one
module has to know every operation's types. The representations
live in `Ghostty.Effectful.Internal.*`; the public modules export the types without constructors.
Unlike §2.7's subsystems it has **one interpreter**: libghostty-vt is headless and deterministic, so
the library itself is what tests run against, and a fake would test only the fake. That leaves
dynamic dispatch nothing to buy but interposition (tracing every call), which nothing needs, at the
cost of one GADT and one handler case per operation across M1.5–M1.9 (dynamic was tried in M1.4's
first draft, through `makeEffect`). The representation holds the owner thread (§4.6) and the count
of open handles (`openTerminals`, which is how release is tested); there is no allocator to hold,
since the binding passes the library's default (§3.3). A grid's extent is an `Extent`, a `Word16` that is never
zero (`extent :: Word16 -> Maybe Extent`), because `terminal_new` and `terminal_resize` refuse zero,
so that refusal cannot be expressed and the remaining failure of each is out of memory.

The rank-2 `s` makes a `Terminal s` unusable outside `withTerminal`, so the handle cannot outlive
its `free`. Every region parameter (`Terminal`'s, `TrackedRef`'s, `RenderState`'s, `Frame`'s and
`Row`'s two, the encoders') has a nominal role, declared with `type role`, as `ST`'s is: GHC infers
a phantom one, which lets `coerce` take a handle out of its region without its constructor
(regression 14). `bracket`-style release runs on exceptions. The same pattern scopes encoders and search
sessions. A key or mouse encoder (M1.9) owns the one event handle it encodes from, so an encode
fills that in rather than making an event per keystroke; a mouse encoder keeps state between events
(the last cell it reported), which is what makes it a handle. A formatter is not a handle at this
level (M1.8): it reads its terminal afresh at each format, so keeping one buys nothing, and a range
to format is a pair of untracked grid references, valid only until the terminal next changes. So
`format` and `formatRange` each make a formatter, resolve the range's points, format and free it in
one call. The OSC and SGR parsers are not handles either (M1.9): what a parser returns is borrowed
until its next call, so each parse makes one, feeds it one sequence, copies the result out and frees
it. Handles that the application needs to keep for the whole session (the child terminal) are opened
once at the top of `Canopy.App.Run` inside the region, which is fine: the region is the session.

### 4.3 Borrowed data: frames

Render-state iterators and cell data are valid only until the next `render_state_update`. A render
state is a region of its own inside its terminal's, and a frame a second, shorter region inside that:

```haskell
withRenderState
  :: Ghostty :> es
  => Terminal t
  -> (forall s. RenderState s -> Eff es a)
  -> Eff es a

withFrame
  :: Ghostty :> es
  => RenderState s
  -> (forall f. Frame s f -> Eff es a)
  -> Eff es a

dirtyRows :: Frame s f -> Eff es [Row s f]
cells     :: Row s f -> Eff es (Vector Cell)   -- Cell is a copied Haskell value: no index
```

`Row s f` and anything else borrowed carries the frame tag `f`, so it cannot be held across an update.
Data that leaves the frame is **copied** into plain Haskell values (`Cell`, `Style`, `Rgb`,
`Hyperlink`), which carry no tag. The copy is the price of safety, and it is paid only for dirty rows
(§12.1). (M1.7.) A render state gets its own rank-2 region, not its terminal's `s`, because it is
freed before the terminal is: with the terminal's tag it could outlive its `free`.

- **Dirty state belongs to frames.** `withFrame` updates the render state; a frame that returns
  marks its changes consumed (`render_state_clean`), and one that throws does not, so the next frame
  reports them again. `dirtyRows` is the header's dirty iteration: none, the changed rows, or every
  row. Neither dirty option is exposed. A `withFrame` inside another on the same render state is that
  frame: it neither updates nor consumes.
- **The rows are read through one iterator per render state**, reused by every frame. Iterators
  only move forward, so the render state records how far its row iterator has moved and refills it
  only to go back; rows read in order cost one step each.
- **Frame and row data are typed keys** (`FrameData a`, `RowData a`, read with `getF` and `getR`),
  one constructor per header row as in §4.4, prefixed `Render…` and `Row…` so they do not collide
  with the terminal's. Rows without one: the iterators (how rows and cells are read), the bulk raw
  cell view, selection (M6.5), image placements (M6.15), and overscan. **No overscan is requested**:
  overscan is for renderers that shift the grid by part of a row to scroll smoothly, and canopy draws
  whole rows into a host terminal. A cursor value the header calls undefined outside the viewport is
  `Nothing`. The cell keys a copy reads into `Cell` are held against the header the same way.
- **A synchronized-output hold shows the frame from when it began** (§4.5's question, answered).
  When a program sets mode 2026, the terminal holds exactly the frame the program wants left on
  screen, but the bytes after it are processed in the same write, and `vt_write_until` cannot stop
  at a CSI. The header's answer is to update the render state inside the `RENDER_HOLD` callback. That
  is a C call, and §4.1's third goal keeps Haskell out of callbacks, so the callback is C
  (`cbits/gveff_terminal.c`): it updates every render state attached to the terminal and marks each
  held, then calls the Haskell callback that appends the `RenderHold` event. Until the hold ends,
  `withFrame` does not update a held render state (`frameHeld` says so). The terminal has no clock,
  so ending a hold that lasts too long is the caller's, by turning the mode off; that calls no
  callback, so `setT` drops every capture of the terminal itself when it turns the mode off. (It
  was first noticed lazily, by `withFrame` reading the mode, but turning the mode off and on again
  before a frame then brought the old hold's frame back.) A hold that begins while
  a frame of a render state is open is not captured into it, because the update would invalidate the
  rows being read; that render state shows the terminal live after.
- **A hyperlink's URI is not in the render state**, only whether a cell has one. It is read from the
  terminal at the cell's viewport position, which is right only while the terminal is the frame's
  moment. So each terminal counts the calls that change it, a frame records the count, and a linked
  cell's `uri` is `Nothing` in a held frame or once the count has moved.

### 4.4 Typed keys

The header's tables become GADTs (`Ghostty.Effectful.Terminal.Keys`):

```haskell
data TerminalData a where
  Cols            :: TerminalData Word16
  CursorX         :: TerminalData Word16
  CursorY         :: TerminalData Word16
  Title           :: TerminalData Text           -- empty when unset; the header never says NO_VALUE
  ActiveScreen    :: TerminalData Screen         -- Primary | Alternate
  Mode            :: ModeKey r -> TerminalData Bool
  ColorForeground :: TerminalData (Maybe Rgb)    -- NO_VALUE when none is set
  KittyKeyboardFlags :: TerminalData KittyFlags
  -- …one constructor per header row

data TerminalOption a where
  SetTitle        :: TerminalOption Text
  SetColorForeground :: TerminalOption (Maybe Rgb)  -- Nothing is the header's NULL: unset
  SetMode         :: ModeKey r -> TerminalOption Bool
  SetModeDefault  :: ModeKey 'Configurable -> TerminalOption Bool
  -- …

getT :: Ghostty :> es => Terminal s -> TerminalData a -> Eff es a
setT :: Ghostty :> es => Terminal s -> TerminalOption a -> a -> Eff es ()
```

`NO_VALUE` is not an error: for keys where the header says a value may be absent, the GADT's index is
`Maybe`, and the marshalling for that constructor maps `NO_VALUE` to `Nothing`. For keys where it
cannot happen, it is an internal invariant violation (§4.7). `INVALID_VALUE` for a key cannot happen
at all: the constructors are the only keys. An option takes a `Maybe` exactly where the header's
null pointer means something no value of the type says (unset a colour, remove a limit, restore the
built-in palette); where null only equals some value (`DEFAULT_CURSOR_BLINK`'s null is "not
blinking"), the option takes the plain type. Since libghostty-vt 1.0 a null value restores the
option's default, so where `Nothing` means something other than the default the binding passes the
header's own value for it: no scrollback byte limit is `SIZE_MAX`, since the default is 10,000 bytes
(M1.11, regression 11).

What a write would refuse is kept out by the value's type, as `Extent` does for zero (§4.2):

- **`ModeKey r`** names the modes the library recognises (`Ghostty.Effectful.Mode`), indexed by
  whether `MODE_DEFAULT` accepts them. The library refuses a reset default for modes whose set or
  reset does more than flip a bit (the alternate screens, the mouse protocols, synchronized output,
  origin, …); those are `ModeKey 'Fixed` and `SetModeDefault` cannot take them. The test suite
  checks the index of every mode against the linked library through the raw call, and that the
  list is every mode the library answers a `MODE` read for, by asking about all 2¹⁶ mode numbers.
- **`TerminfoName`** is at most 128 bytes (`terminfoName :: Text -> Maybe TerminfoName`), and
  **`ChecksumExtension`** is a record of the five XTCHECKSUM bits, so a value above 31 is
  unrepresentable.

Three groups of header rows have no constructor, each for a reason: the callback options and
`USERDATA`, which the binding installs itself and never lets a caller (§4.5), except the six whose
callback answers the program, each of which is an option that sets the answer (`SetColorScheme`,
`SetDeviceAttributes`, `SetEnquiry`, `SetXtversion`, `SetSize`, `SetClipboardWrite`); `SELECTION` both ways,
whose value is a pair of grid references and arrives with the selection API (M6.5); and the
`KITTY_GRAPHICS` data key, a borrowed handle, with image placements (M6.15). A test holds the
constructors plus this list against the header's enums, so a row a pin bump adds fails it. A
constructor is named for its row (`CursorX` for `GHOSTTY_TERMINAL_DATA_CURSOR_X`, `SetTitle` for
`GHOSTTY_TERMINAL_OPT_TITLE`), and a test holds each name against the number its marshalling sends,
so two keys of the same type and fresh value cannot be swapped unnoticed.

The marshalling for each constructor is a `Storable`-level `peek` at the right type, written once per
constructor (`Ghostty.Effectful.Internal.Keys`). The values are plain Haskell types in their own
modules, so that §4.3's frames reuse them: `Rgb` and `Palette` (`.Color`; a palette has a colour at
every `Word8`), `Style` (`.Style`), `Point (c :: Coord)` (`.Point`). A test enumerates the
constructors (`[Some TerminalData]`, kept exhaustive by a `-Wincomplete-patterns` match in the test)
and calls each on a fresh terminal against its expected value; another writes every option and
reads it back where a key reads the same setting. The same treatment applies to render-state data,
row and cell data (§4.3).

**Tracked grid references** (`TrackedRef s`) follow a cell as the terminal scrolls, prunes and
reflows; blocks are pairs of them (§7.3). A terminal owns the references made from it in a registry,
and `withTerminal` frees whichever are left when its region ends. A reference names its registry
entry, not the C handle, so `untrack` is idempotent, and a reference that was untracked reports no
point and cannot be moved: it is never passed to the library again. `untrack` exists because each
live reference costs the terminal work on every scroll, and a session's blocks accumulate. Points
carry their coordinate system in their type (`refPoint @'Grid`), and a point outside it is
`Nothing`, which the header documents as `INVALID_VALUE` for a valid terminal. One such point the
library does not refuse: a scrollback (`History`) row past the end of the scrollback resolves to the
active row that many rows down (at the pin, `PageList.pin` bounds a history row only by the whole
screen). So every call that takes a point checks a `History` row against `SCROLLBACK_ROWS` first
(M1.8, regression 6). Conversely, the library reads a reference to an active-area cell back as a
`History` row past the scrollback, so `refPoint @'History` is `Nothing` for any cell with an `Active`
position (regression 7).

### 4.5 Callbacks become events

C callbacks are installed by the binding, never by users, and each does exactly one thing: append a
constructor to an `IORef`'d buffer owned by that terminal, or, for a prompt mark, a copy to a list
in C (below, D18). `feed` drains both:

```haskell
feed :: Ghostty :> es => Terminal s -> ByteString -> Eff es [TerminalEvent]

data TerminalEvent                     -- Ghostty.Effectful.Event
  = WritePty ByteString                -- replies to the child's queries; caller writes them to the PTY
  | Bell
  | TitleChanged Text
  | PwdChanged Text
  | SemanticPrompt PromptMark          -- OSC 133: A/B/C/D with parameters (§7.3), and the cursor
  | ClipboardWrite ClipboardLocation [ClipboardContent]
  | Notification Text Text
  | Progress ProgressReport
  | ProgramStatus ProgramReport        -- OSC 7501
  | RenderHold Bool                    -- synchronized output, mode 2026
  | UnknownSequence UnsupportedSequence
  | Reset
  | ResizeRequest WindowSize           -- CSI 8 t; Nothing keeps an axis
```

Events come back in the order the bytes produced them, which matters: a `SemanticPrompt C` must be
seen at the right point in the stream so that the output range it opens starts at the right row. To
get that, `feed` writes with `ghostty_terminal_vt_write_until(…, GHOSTTY_TERMINAL_BOUNDARY_OSC_END,
…)`, which stops right after each OSC terminator and reports how much it consumed. After each stop,
the buffer is drained and resolved: a `SemanticPrompt` gets `CURSOR_X`/`CURSOR_Y`, and a title or
working-directory change gets the new value (their callbacks carry none). Then the write continues
with the rest of the chunk. The header forbids calling `vt_write` from inside a callback, which this
never does: the terminal is read between writes, not inside them. (Checked, M1.6: an OSC ended by
`ESC \` is dispatched at the `ESC`, where `vt_write_until` stops, so its mark's cursor is right too;
and the same stream split at every byte gives the same events.) Adjacent `WritePty`s are joined, so
one reply is one write: across stops, and with any events buffered before the write.

A callback must not let an exception into C, so each body is guarded: an exception is recorded in
the buffer and thrown by the drain, after the write. So is a C enum value the binding does not name
(`UnknownEnum`, §4.7), which a callback cannot throw. A failure while resolving one stop's events does
not stop the write: every byte is written, so the terminal never falls behind the program's output,
and the first failure is thrown after. `resize` and `reset` call callbacks too (the end of a render
hold, mode 2048's in-band size report), so they return `[TerminalEvent]` as `feed` does. `setT`
returns `()`: the header says setting a mode never invokes a callback, not even the end of a render
hold, and a test writes every option and finds nothing buffered, so a pin bump that changes this
fails it. An event left by a call that threw before returning it comes first in the next `feed`.

**Query callbacks are configuration, not callbacks.** Colour scheme, device attributes, enquiry,
XTVERSION and size are answered from `TerminalConfig`, which the caller can update with `setT`
(`SetColorScheme`, `SetDeviceAttributes`, `SetEnquiry`, `SetXtversion`, `SetSize`: options named for
their callback's row, §4.4). No user code runs during a query; the answers are data that a test can
inspect. Size is answered from the terminal's own grid and cell size, kept by `resize`. A device
attributes callback that declines gets the library's defaults (VT220 with ANSI colour), not silence,
so `defaultDeviceAttributes` is those and the callback always answers. ENQ and XTVERSION are answered
by a callback that returns a `GhosttyString` by value, which no Haskell function can be (§3.3), so
those two answers are returned by C (`ghostty-effectful/cbits/gveff_terminal.c`) from bytes the
binding owns, reached through `USERDATA`. A clipboard write must be answered before its callback
returns, so whether to accept it is configuration too (`SetClipboardWrite`, off by default): accepted,
it is an event and the program is told it succeeded; refused, it is dropped and the program told it
was denied. `CLIPBOARD_READ` is never installed, so a program's clipboard read is answered as empty;
installing it would also turn on kitty paste events, which nothing wants yet.

A render hold's frame was a question for M1.7: the header asks the embedder to capture the frame in
the `RENDER_HOLD` callback, because by the time the write returns the bytes after mode 2026 was set
have been processed, and `vt_write_until` cannot stop at a CSI. The event comes in order, but the
frame it points at is gone by then. Answered in §4.3: the callback is C, captures into each render
state of the terminal, and then calls the Haskell callback, which only appends, as every other does.
The terminal's `USERDATA` is one C struct (`GveffUserdata`): the two answer strings, first, the
render states a hold captures into, and the prompt marks.

**A prompt mark is copied in C** (D18). A call from C into Haskell makes a Haskell thread, and in a
stream of marks that was most of a mark's cost (§12.3). So `SEMANTIC_PROMPT` is C: it copies the
event, its command and error strings too, onto a list in the `USERDATA`, and no Haskell runs. A drain
takes the Haskell buffer, then the C list (`takeMarks`), and resolves both as before. That order is
the stream's because the feed stops after every OSC: a mark ends its stop, so nothing the Haskell
callbacks append comes after it. A write that did not stop at each OSC would need the marks
sequenced against the buffer, and no other call produces marks: `resize`, `reset` and `paste` cannot.
A mark C cannot copy for want of memory is dropped and recorded, and the drain throws `OutOfMemory`
after the write, as it throws a Haskell callback's exception. A drain with no marks makes one
`unsafe` call and allocates nothing.

### 4.6 Concurrency

libghostty handles are not thread-safe. `ghostty-effectful` does not try to make them so; all calls on
one handle family must come from one thread. Two mechanisms, one static and one dynamic:

- **Statically, the loop cannot fork.** Feeder threads are started in `Canopy.App.Run` *before*
  `runGhostty` is introduced, in an effect row that does not contain `Ghostty`; the event loop then
  runs in a row that contains `Ghostty` and does *not* contain `Concurrent`. Nothing in the loop can
  call `forkIO`, so nothing can carry `Ghostty` to another thread. §2.6 rule 4 already keeps
  `Effectful.Concurrent.**` out of the core's imports.
- **Dynamically, the handler checks its owner.** `runGhostty` records `myThreadId` and every
  operation compares against it (one `myThreadId`, cheap next to an FFI call), throwing
  `WrongThread` on mismatch, before any C call. A static operation runs on its caller's thread, so
  the check sees the caller.
  This is needed because effectful's own `forkIO` *clones* the environment
  (`Effectful.Internal.Env.cloneEnv`), so an effect in scope at a fork is usable in the child thread;
  only `withEffToIO SeqUnlift` checks the thread (`Effectful.Internal.Monad.seqUnliftIO`, effectful-core
  2.7.1.2), and that does not cover forks. The check turns a misuse into an immediate exception at the
  first call rather than a data race, and §10.5 records it as one of the few runtime checks.

### 4.7 Errors

```haskell
data GhosttyError                       -- thrown
  = OutOfMemory CallSite
  | WrongThread CallSite                -- §4.6
  | Invariant CallSite ResultCode       -- the library returned what the header says it cannot
  | UnknownEnum CallSite Text Integer   -- a C enum value the binding does not name (§3.3)
```

The version check and the layout test rule `UnknownEnum` out. (Until M1.11 there was a
`ShortStruct`, for a sized struct a callback received with a smaller `size` than the binding reads.
At libghostty-vt 1.0 every struct a callback receives is frozen, with no `size`, so it went.) The
library's `UNSUPPORTED` (`ResultUnsupported`), for a key it does not know or a feature compiled
out, is only ever an `Invariant`: the exact version check (§3.4) refuses a library without every
feature, and the binding names no key the pinned library lacks.

`ResultCode` is `GhosttyResult` closed, with an unknown case (§3.3), so no `Ghostty.FFI` type
escapes. `CallSite` names the C function, or the operation for `WrongThread`. Errors a caller can
act on are not here: `Rejected` (unsafe paste, §8.5) is its own type, returned as `Either` from the
one operation that can produce it (`paste`, M1.9), and `LimitExceeded` joins `GhosttyError` with the
first bound call that can return it. A too-small buffer is handled inside the `*_alloc` variants and
never escapes, so it has no constructor. Out of memory, wrong-thread use and invariant violations are
thrown as exceptions, because no caller can do anything useful with them and threading them through
every signature would hide the errors that matter. The version check in `runGhostty` returns
`Either VersionMismatch` and is the only way to obtain the effect.

## 5. `tendril` — the line editor

### 5.1 What it is

A readline library in the lineage of haskeline, reedline (nushell) and prompt_toolkit: everything a
REPL needs to read one possibly multi-line input with highlighting, completion menus, hints,
validation and history, rendered inline in the host terminal. It is useful without canopy, and
`tendril-demo` proves that.

It is designed around reedline's decomposition — highlighter, hinter, completer, validator, menu,
prompt, history and edit mode as independent pluggable parts — but expressed as **effects**, not
traits or callbacks: the application interprets them, which is how canopy plugs in tree-sitter and
LSP without tendril knowing either exists.

### 5.2 Layers

| Layer | Modules | IO? |
| :--- | :--- | :--- |
| T0 text | `Tendril.Text.Units`, `Tendril.Text.Buffer`, `Tendril.Text.Grapheme`, `Tendril.Text.Width` | no |
| T1 editing | `Tendril.Edit.Command`, `.Motion`, `.Undo`, `.KillRing`, `.Selection`, `.Register` | no |
| T2 modes | `Tendril.Keymap`, `Tendril.Keymap.Emacs`, `.Vi`, `.Helix` | no |
| T3 widgets | `Tendril.Widget.Menu`, `.Hint`, `.Popup`, `.Prompt`, `.Search` | no |
| T4 layout | `Tendril.Render.Style`, `.Doc`, `.Layout`, `.Grid`, `.Diff` | no |
| T5 terminal | `Tendril.Term.Input` (decoder), `.Output` (VT emitter), `.Tty` (raw mode, size, SIGWINCH), `.Caps` (capability probing) | decoder and emitter no; `.Tty` yes |
| T6 driver | `Tendril.Effect`, `Tendril.Run` | yes |

T0–T5's pure parts are where nearly all the logic and all the property tests are.

### 5.3 Text, positions and units

The buffer is a `text-rope` rope (`Data.Text.Mixed.Rope`, which maintains code-point, UTF-8 and
UTF-16 metrics in one structure, with `charSplitAtPosition`, `utf8SplitAtPosition` and
`utf16SplitAtPosition`). On
top of that tendril adds grapheme clusters and display width. Positions carry their unit in their
type (§10.1):

```haskell
newtype Offset (u :: Unit) = Offset Word
data Unit = Byte | Utf16 | CodePoint | Grapheme | Column
```

The cursor is an `Offset 'Grapheme`, so it can never be inside a cluster; tree-sitter talks in
`Offset 'Byte`; LSP in `(Line, Offset 'Utf16)`; the renderer in `Offset 'Column`. Conversions are
functions of the buffer, never `coerce`s.

**Width is the terminal's decision, not tendril's.** Grapheme segmentation (UAX #29) and width
tables are generated by tendril itself: `scripts/gen-unicode-tables.py` reads the Unicode Character
Database at a pinned version (`GraphemeBreakProperty.txt`, `emoji-data.txt`, `EastAsianWidth.txt`,
`DerivedCoreProperties.txt` for `InCB`) and writes `Tendril.Text.Unicode.Tables`, which is committed
and regenerated deliberately. No Hackage package provides this without ICU: `unicode-data` 0.9.0 has
neither the grapheme-break property nor East Asian width, and `text-icu` would make every tendril user
install ICU. `Tendril.Term.Caps` probes the host for grapheme-cluster mode (mode 2027) and adjusts. Mismatched
width tables are the classic source of line editors corrupting the screen; the test suite compares
tendril's widths against libghostty's for every codepoint and a corpus of clusters (§11.2), and the
remaining risk is a host that disagrees with both (§14.3).

### 5.4 Edit commands and keymaps

Every edit is a value:

```haskell
data Command (m :: ModeKind) where
  Insert        :: Text -> Command m
  Move          :: Motion -> Command m
  Delete        :: Motion -> Command m
  Kill          :: Motion -> Command m
  Yank          :: Command m
  Undo, Redo    :: Command m
  AcceptOrNewline :: Command m         -- asks the validator (§5.5)
  ForceNewline  :: Command m
  HistoryPrev, HistoryNext :: Command m
  HistorySearch :: SearchKind -> Command m
  OpenMenu      :: MenuId -> Command m
  ExpandSelection, ShrinkSelection :: Command m    -- structural, via Structure effect
  EditExternal  :: Command m           -- $EDITOR
  App           :: AppCommand -> Command m          -- opaque to tendril; canopy's commands
  -- vi-only
  ViOperator    :: Operator -> Command 'ViNormal
  ViEnterInsert :: InsertWhere -> Command 'ViNormal
  ViEscape      :: Command 'ViInsert
  -- …
```

The `ModeKind` index means a vi operator cannot be bound in an Emacs keymap, or an insert-only
command in normal mode, **in the built-in keymaps, at compile time**. A keymap is
`Keymap m = Trie KeyChord (Command m)`. User keybinding files are parsed into the same type at
startup by a decoder that checks the mode of every bound command and reports all errors at once;
after load there is no unbound or ill-moded command left to discover.

`AppCommand` is a type parameter in the real signature (`Command app m`), so the application's own
commands (canopy's "rewind", "select previous block") are bound in the same tries with the same
checks.

**Undo** is a tree, not a stack (as in vim and helix), with edit coalescing by command kind and time.
**History** is an effect (§5.5) whose default interpreter is an append-only file; canopy's
interpreter is SQLite-backed with context (§8.8).

### 5.5 Plug-in points are effects

```haskell
data Highlighter :: Effect where
  Highlight :: Revision -> Rope -> Highlighter m Spans
data Completer :: Effect where
  Complete  :: Revision -> Rope -> Offset 'Grapheme -> Completer m (Async CompletionList)
data Hinter :: Effect where
  Hint      :: Revision -> Rope -> Offset 'Grapheme -> Hinter m (Maybe Hint)
data Validator :: Effect where
  Validate  :: Rope -> Validator m Validity     -- Complete | Incomplete Indent | Invalid Diag
data Structure :: Effect where
  Enclosing :: Rope -> Range 'Grapheme -> Structure m (Maybe (Range 'Grapheme))
data History :: Effect where
  …
```

Each comes with trivial interpreters (no highlighting, word completion over history, always-complete
validation, bracket-matching structure) so that `tendril-demo` is a useful readline out of the box.

**Slow plug-ins never block typing.** The completer returns an `Async`; results are tagged with the
`Revision` (a counter incremented on every buffer change) they were computed for, and a result whose
revision is older than the buffer's is dropped (reedline lists exactly this as unsolved). Highlighting
is required to be fast and synchronous; canopy meets that with incremental tree-sitter and layers
slow semantic highlighting on top asynchronously (§9.1).

### 5.6 Rendering to the host

Tendril renders **inline**, like ptpython and reedline: the live region (prompt, input, menu, hints,
popups) occupies the bottom of the host screen, and completed output is *committed* above it into the
host's native scrollback, so the host's own scrolling, search and selection keep working.

```haskell
data Surface = Surface
  { live    :: Doc        -- redrawn every frame
  , commits :: [Doc]      -- printed once, above the live region, then forgotten
  }
```

- `Doc` is a styled layout language (rows of styled spans, boxes for popups, a cursor position).
  `Layout` turns it into a `Grid` of cells at the current width.
- `Diff` compares the new grid with the previous one and emits the minimal VT; `Output` emits it
  wrapped in synchronized-output mode (2026) when the host supports it, so the user never sees a half
  frame.
- **Committing above the live region** is erase-live-region, print commit, redraw live region; this is
  reedline's "external printer" and is how canopy shows child output that arrives *while the user is
  typing* (§8.3).
- A full-screen mode (alternate screen, own scrollback) is designed for but not built first;
  `Surface` already distinguishes the regions it would need. D-deferred-4.

### 5.7 Host input

`Tendril.Term.Input` is a pure, incremental decoder from host bytes to events:

```haskell
data InputEvent
  = Key KeyEvent            -- with modifiers, press/repeat/release, text, shifted/base keys
  | Paste Text              -- bracketed paste, already un-bracketed
  | Mouse MouseEvent        -- SGR (1006) and SGR-pixels
  | Focus Bool
  | Resize Size
  | Reply TerminalReply     -- DA, DECRQM, colour queries, kitty-keyboard query, OSC 52 read
```

It understands legacy encodings (with the usual ESC-timeout ambiguity resolved by a configurable
timeout, and *not needed* once the kitty keyboard protocol is negotiated), CSI-u / the kitty keyboard
protocol with all enhancement flags, xterm's modifyOtherKeys, bracketed paste, SGR mouse and focus.
`Tendril.Term.Caps` probes the host at startup (DA1 as a sentinel after DECRQM/kitty queries, so
unanswered probes time out deterministically) and enables the best protocol available.

libghostty-vt has encoders but no decoder; the decoder is tendril's. The roundtrip test — ghostty's
encoder produces bytes for a generated key event under generated modes, tendril decodes them, the
event comes back equal — is the strongest test in the package (§11.2).

### 5.8 The driver

```haskell
data LineEditor :: Effect where
  ReadInput :: PromptSpec -> LineEditor m ReadResult    -- Submitted Text | Eof | Interrupted
  Commit    :: Doc -> LineEditor m ()                    -- print above the live region
  Redraw    :: LineEditor m ()
```

`runLineEditor` owns the TTY: raw mode entered and restored with `bracket` (and on `SIGTSTP`/`SIGCONT`,
and on fatal signals, so a crash never leaves the user's terminal raw), the SIGWINCH handler, the
input thread. For canopy, which needs to interleave host input with child output, tendril also exports
the pieces separately — the pure `EditorState`, `step :: InputEvent -> EditorState -> (EditorState,
[Effect])`, and the renderer — so the application can drive the editor from its own event loop
instead of from `ReadInput`. `ReadInput` is that loop specialised to "the only event source is the
keyboard".

## 5A. `tree-sitter-ffi` — the low-level binding

(Numbered 5A and 5B rather than renumbering §6 onwards, because section numbers are cited, §2.9.)

### 5A.1 The runtime is vendored

Unlike libghostty-vt, tree-sitter's runtime is plain C11 with no build system requirement: the
library ships a single-file amalgamation, `lib/src/lib.c`. So it is **vendored**, not linked:

- `tree-sitter-ffi/vendor/tree-sitter/` holds `lib/src/`, `lib/include/` and the MIT `LICENSE` at a
  pinned release tag, recorded in `tree-sitter-ffi/TREE_SITTER_VERSION` (`v0.27.1` at the time of
  writing). `scripts/vendor-tree-sitter.sh <tag>` replaces the tree, and a bump is one deliberate
  commit that changes the tag, regenerates the shims (§5A.2) and says why.
- The cabal file compiles it with `c-sources: vendor/tree-sitter/lib/src/lib.c` and
  `include-dirs: vendor/tree-sitter/lib/include vendor/tree-sitter/lib/src`, with
  `cc-options: -std=c11 -O2 -D_POSIX_C_SOURCE=200112L -D_DEFAULT_SOURCE`. The optional WebAssembly
  grammar store (`TREE_SITTER_FEATURE_WASM`) is not enabled; it would pull in wasmtime.
- **Header/library drift is impossible by construction**: the headers `hsc2hs` reads and the code
  that is linked are the same files, compiled in the same package. That is why this package needs no
  equivalent of §3.4's layout test — and why vendoring is preferred to a system `libtree-sitter`
  through pkg-config, whose version a user's distribution decides.
- The runtime accepts grammars of language ABI `TREE_SITTER_MIN_COMPATIBLE_LANGUAGE_VERSION` to
  `TREE_SITTER_LANGUAGE_VERSION` — 13 to 15 at v0.27.1 — and both constants are exported, so the
  high level reports a precise error for a grammar outside the range (§5B.4).

### 5A.2 By-value structs need shims

tree-sitter's API passes small structs **by value**: `TSNode` (a 32-byte struct holding a context
array, an id and a tree pointer), `TSPoint`, `TSRange`, `TSTreeCursor`, `TSParseOptions` and others,
both as arguments and as results — `TSNode ts_node_child(TSNode self, uint32_t child_index)`.
GHC's FFI cannot pass or return a struct by value. Every such function (56 of them in v0.27.1's
`api.h`, counting every by-value `TSNode`, `TSPoint`, `TSRange`, `TSTreeCursor`, `TSInput`,
`TSParseOptions` and `TSLogger`) gets a C shim that takes pointers instead:

```c
void tsffi_node_child(const TSNode *self, uint32_t child_index, TSNode *out) {
  *out = ts_node_child(*self, child_index);
}
```

- **The shims are generated**, by `scripts/gen-ts-shims.py` from the vendored `api.h`, into
  `cbits/tsffi_shims.c` and `include/tsffi_shims.h`, and committed. CI runs the generator in
  `--check` mode (§2.8 step 3), so a bump that changes a prototype cannot leave a stale shim. Hand-
  writing 56 near-identical wrappers is how one of them ends up dereferencing the wrong argument.
  (`hs-tree-sitter-capi` solves the same problem with `hsc2hs` `#{def}` blocks written by hand.)
- **Every import is `capi`**, against `api.h` for the functions that take only scalars and pointers
  and against `tsffi_shims.h` for the rest, so the C compiler checks each Haskell signature against a
  real prototype as far as it can (§3.3's reason). §3.3 found that this misses integer widths and
  pointers to Haskell types, so `tree-sitter-ffi` gets a signature check like ghostty's when its
  functions are bound (M4.1).
- Structs and enums come from `hsc2hs`, as in §3.3; `TSSymbol`, `TSFieldId` and `TSStateId` are
  `Word16` newtypes, and C enums are newtypes with `COMPLETE` pattern synonyms, open for the same
  reason as §3.3's.

### 5A.3 No Haskell runs inside tree-sitter

tree-sitter has four callback points: the parse progress callback, the query-cursor progress
callback, the `TSInput` reader (for parsing non-contiguous text) and the logger. **None of them is a
Haskell function.** Each is supplied in C:

- **Progress** (both kinds) is `tsffi_budget_progress`, which reads a `TsffiBudget` the caller passes
  as the payload: a cancellation word and a monotonic deadline in nanoseconds. It returns `true`
  (stop) when the word is set or `clock_gettime(CLOCK_MONOTONIC)` passes the deadline. Haskell sets the
  word with an atomic write to pinned memory; nothing re-enters the RTS.
- **Input** is always a contiguous UTF-8 buffer, through `ts_parser_parse_with_options` with a C
  reader (`tsffi_buffer_read`) over a pointer and length. REPL inputs and shadow documents are small
  enough that copying a rope into one buffer per parse costs less than a callback per chunk.
  D-deferred-8 holds the trigger for a chunked reader.
- **Logging** and DOT-graph output are not bound.

So no tree-sitter call can call back into Haskell, and the `safe`/`unsafe` choice is purely about
duration: **`safe` for calls that can run long** — `ts_parser_parse_with_options`,
`ts_query_cursor_exec_with_options` and `ts_query_cursor_next_match`/`next_capture`, `ts_query_new`
(query compilation is not cheap on large queries) — so that a long parse does not block the other
Haskell threads, and `unsafe` for everything else (node accessors are nanoseconds). The rule is
recorded on each import, as in §3.3.

### 5A.4 What it exposes

`TreeSitter.FFI.Api` (the imports), `TreeSitter.FFI.Types` (`hsc2hs` structs and enums),
`TreeSitter.FFI.Shims` (the generated imports), `TreeSitter.FFI.Budget`, and
`TreeSitter.FFI.Language`, which turns a `FunPtr (IO (Ptr TSLanguage))` obtained from `dlsym` into
a language pointer (a `capi "dynamic"` import), the one piece of grammar loading that needs FFI.
Raw types only, no `ForeignPtr`, no exceptions, as in §3.3. Statically linked grammars (the test
suites', §5B.7) are reached by an ordinary `foreign import capi "tree_sitter_json"` in the package
that compiles their `parser.c`.

## 5B. `tree-sitter-effectful` — the high-level binding

### 5B.1 Goals

1. **No dangling nodes and no stale trees**, by types: a node keeps its tree alive, and a tree that
   has been edited but not re-parsed cannot be queried.
2. **Reading a syntax tree is pure.** Trees are values, so highlighting, completeness and structural
   queries are ordinary functions that canopy's pure core can call (§2.6 rule 4).
3. **Typed node kinds and fields for grammars known at compile time**: a misspelt `"import_statment"`
   is a compile error, not a query that silently never matches.
4. **Queries are compiled once with typed captures**, and every capture name is accounted for.
5. **Parsing is cancellable and confined** to the thread that owns the parser.

### 5B.2 Persistent trees, pure reads

```haskell
data Language (g :: Grammar)   -- a loaded grammar; g is 'Dynamic or 'Known name (§5B.4)
data Tree g                    -- ForeignPtr TSTree with a ts_tree_delete finalizer, plus its source
data Node g                    -- a copied TSNode plus the Tree's ForeignPtr, which keeps it alive
data EditedTree g              -- an edited tree: input to the next parse, and nothing else
```

**Trees are never mutated once a Haskell value refers to them.** `edit` copies first —
`ts_tree_copy` is an O(1) shallow copy that bumps the root's reference count — and edits the copy:

```haskell
edit :: [InputEdit] -> Tree g -> EditedTree g
```

The old `Tree` and every `Node` taken from it stay valid and unchanged. The result is an
`EditedTree`, whose only use is as the old tree of the next `parse` (§5B.3); its node positions have
been shifted but its source has not, so it is not a `Tree` and has no node API. Querying an edited,
unparsed tree — a classic tree-sitter bug that produces plausible-looking wrong ranges — is a type
error.

**A `Tree` carries the bytes it was parsed from**, so `nodeText :: Node g -> ByteString` is total and
query predicates (§5B.5) need no extra argument that could be the wrong source.

**Node reads are pure functions**: `kind`, `symbol`, `range`, `children`, `namedChildren`,
`childByField`, `parent`, `nextSibling`, `hasError`, `isMissing`, `isError`,
`namedDescendantForRange`, `toSExpr`, and folds over the tree (implemented with a `TSTreeCursor`
created and freed inside the fold). They are implemented in **one module, `TreeSitter.Internal.Pure`,
with `unsafeDupablePerformIO`** over `unsafe` FFI calls — the package's only use of an unsafe
primitive, private by §2.6 rule 5, and listed in the unsafety audit (§10.6). Purity is justified by
the runtime's source (§14.2): node functions only read subtrees (the only assignments in `node.c` are
to stack-allocated iterators), subtree reference counts are atomic (`atomic_inc`/`atomic_dec` in
`subtree.c`), and the only operations that write a tree are `ts_tree_edit` and `ts_tree_delete`,
which the API above never applies to a tree that another value can see (edits apply to a fresh copy;
deletion runs from the finalizer, when no value refers to that copy).

**So `Language`, `Tree`, `Node` and `Query` can be shared between threads.** The header's warning that
"syntax trees are not thread safe" and must be copied for use on another thread is about exactly
those two writes; with copy-on-edit and finalizer-only deletion every `Tree` value is its own copy and
is never written. The parser and query cursors are mutable and are not shared (§5B.3, §5B.5).

Positions are tree-sitter's own, typed: `ByteOffset` and `Point { row :: Row, column :: ByteColumn }`,
newtypes without `Num`. **An `InputEdit` cannot be built from raw numbers.** Its only constructor is

```haskell
splice :: ByteString -> ByteOffset -> ByteOffset -> ByteString -> InputEdit
       -- old source, start, old end, replacement
```

which computes the start, old-end and new-end *points* by counting newlines in the given bytes.
Inconsistent byte/point pairs are the other classic incremental-parsing bug, and this makes them
unrepresentable. Canopy converts tendril's grapheme-indexed edits into `splice`s in one adapter
(§9.1).

### 5B.3 The parser effect

```haskell
data Parse :: Effect            -- static dispatch; owns one TSParser per Language in use

runParse :: IOE :> es => Eff (Parse : es) a -> Eff es a

parse
  :: Parse :> es
  => Language g
  -> Maybe (EditedTree g)       -- the previous tree, edited: incremental parse
  -> ByteString                 -- the new source, UTF-8
  -> Budget                     -- deadline and cancellation token
  -> Eff es (Either Aborted (Tree g))

changedRanges :: Tree g -> Tree g -> [Range]    -- pure; ts_tree_get_changed_ranges
```

- **Confinement** follows §4.6 exactly: `runParse` records its thread and every operation checks it,
  and canopy runs the effect only where `Concurrent` is absent from the row. A `TSParser` is mutable
  state and must not be shared; the trees it produces may be (§5B.2).
- **Budgets** are §5A.3's C-side progress check. `Aborted` says whether the deadline or the token
  stopped it, and the previous tree is still valid, so a caller can keep showing the last good
  highlighting. `cancel :: CancelToken -> IO ()` is safe to call from any thread.
- The previous tree is optional, and passing a tree from a different `Language` is a type error
  (the `g` must match).
- A second interpreter, `runParseIsolated`, creates and frees a parser per call, for tests and for
  one-off parses from worker threads.

### 5B.4 Grammars and typed node kinds

```haskell
data Grammar = Dynamic | Known Symbol
```

**Dynamic grammars** are loaded at run time, which is what language-agnosticism needs:

```haskell
loadGrammar
  :: IOE :> es
  => FilePath -> Text                       -- the shared object, the language name
  -> Eff es (Either LoadError (Language 'Dynamic))
```

It `dlopen`s the object (`System.Posix.DynamicLinker`), looks up `tree_sitter_<name>`, and checks
`ts_language_abi_version` against the runtime's range (§5A.1). `LoadError` distinguishes a missing
file, a missing symbol, and an ABI outside the range with both numbers, which is the error a user
will most often need to read. Node kinds of a `'Dynamic` language are `Symbol` ids with names as
`Text`.

**Known grammars** are those a program's own code is written against — for canopy, the built-in
profiles' (python, haskell, javascript, julia). Every tree-sitter grammar ships
`src/node-types.json`, which lists every named node kind, every field, which fields are required or
repeated, and the supertypes. A Template Haskell splice turns that into types:

```haskell
$(deriveGrammar "python" "grammars/python/node-types.json")
-- generates, among others:
--   data PythonKind  = Module | FunctionDefinition | ImportStatement | … | PythonToken Text
--   data PythonField = FieldName | FieldParameters | FieldBody | …
--   instance KnownGrammar "python"
```

The splice calls `addDependentFile`, so a changed `node-types.json` recompiles. At run time a dynamic
language is **bound** to the known one:

```haskell
bindGrammar :: KnownGrammar n => Language 'Dynamic -> Either (NonEmpty Unresolved) (Language ('Known n))
```

which resolves every generated kind and field to its id with `ts_language_symbol_for_name` and
`ts_language_field_id_for_name`, all or nothing, and reports every name the loaded object lacks. After
that:

```haskell
kindOf    :: KnownGrammar n => Node ('Known n) -> Kind n          -- total
fieldOf   :: KnownGrammar n => Node ('Known n) -> Field n -> Maybe (Node ('Known n))
```

are total functions over closed sums, so code that classifies nodes (§9.2's ghci projection, the
completeness check) gets `-Wincomplete-patterns` coverage, and a node kind or field that does not
exist in the grammar is a compile error. The grammar a known binding expects and the one canopy
fetches come from the same pin (§9.1), so in practice `bindGrammar` fails only on a hand-installed
grammar, and then it fails at load, with names. D-deferred-9 holds the trigger for generating
per-kind typed field accessors from the required/repeated information too.

### 5B.5 Queries

```haskell
data Query g c        -- a compiled TSQuery, its decoded predicates, and a capture-index → c table

class Capture c where
  fromCaptureName :: Text -> Maybe c       -- Text itself is an open instance

compileQuery
  :: Capture c
  => PredicatePolicy -> Language g -> Text
  -> Either QueryError (Query g c)

matches  :: Query g c -> Node g -> Maybe Range -> Limit -> [Match g c]   -- pure
captures :: Query g c -> Node g -> Maybe Range -> Limit -> [(c, Node g)] -- pure, in document order
```

- **`QueryError` carries tree-sitter's error kind and byte offset** (syntax, node type, field,
  capture, structure, language), translated to line and column in the query text, so a bad query
  file reports where it is wrong.
- **Every capture name must decode.** With a closed capture type — canopy's highlight captures, or
  `indent`/`outdent`/`align` for indentation queries — a capture the program does not understand is
  a compile error of the query, at startup, not a capture silently dropped at highlight time. An open
  set uses `Text`.
- **Predicates are applied by this package**, because tree-sitter parses them and leaves their
  evaluation to the host: `#eq?`, `#not-eq?`, `#any-eq?`, `#any-not-eq?`, `#match?`, `#not-match?`,
  `#any-match?`, `#any-not-match?`, `#any-of?`, `#not-any-of?`, and the directives `#set!`, `#is?`
  and `#is-not?`, whose properties are attached to each `Match`. They are decoded at compile time
  into a typed predicate list, so a wrong arity or a capture reference that does not exist is a
  `QueryError` too. Regexes are compiled once, at query compile time (D-deferred-10 holds the choice
  of regex engine).
- **`PredicatePolicy`** says what happens to a predicate this package does not know: `Strict` (an
  error; the default, and what canopy uses for its own queries) or `IgnoreUnknown` (the predicate is
  treated as true; for third-party query collections written for one editor, which use that editor's
  extensions, such as Neovim's `#lua-match?`).
- `matches` and `captures` are pure for the reason in §5B.2: a `TSQuery` is not written during
  execution (the cursor functions take it `const`), and each call creates its own cursor inside
  `TreeSitter.Internal.Pure`, executes with a byte range, a match limit and §5A.3's budget, and
  frees it. Results are fully materialised Haskell values.

### 5B.6 Highlighting

`TreeSitter.Highlight` is the generic highlighter: given a language, its compiled `highlights`,
`injections` and `locals` queries, a resolver from injection language names to languages, and a
tree, it produces non-overlapping styled spans over a byte range, with injected languages parsed
(through `Parse`) and cached per injection site. It is generic because nothing about it is
canopy's: the capture type is a parameter, and how captures become colours (themes, Helix capture
names, fallbacks from `function.builtin` to `function`) is the application's.

### 5B.7 Testing

- **A small grammar is vendored into the test suite**: `tree-sitter-json` at a pinned tag, its
  `parser.c` compiled as the suite's `c-sources` and reached with a static import (§5A.4), so the
  package tests itself without fetching anything. Its `node-types.json` exercises `deriveGrammar`.
- **Properties**: incremental parse after a random edit sequence equals a fresh parse of the final
  text (by S-expression); edits never change the original tree (persistence); `changedRanges` covers
  every byte whose highlighting changed; `splice` agrees with a naive point computation.
- **Concurrency**: a stress test reads the same `Tree` from every capability (`-threaded +RTS -N`)
  while another thread edits and re-parses copies, and checks every read against a single-threaded
  baseline.
- **Queries**: error offsets on malformed queries; predicate semantics on fixtures, cross-checked
  nightly against the `tree-sitter query` CLI's output where the CLI is installed (an oracle, as
  libghostty is for tendril).
- **`bindGrammar`** fails, with the right names, against a grammar whose `node-types.json` differs.

### 6.2 The PTY

The child gets a real pseudo-terminal, because REPLs behave differently on a pipe (no colour, no
prompt, buffered output, sometimes no REPL at all). `Canopy.Child.Pty` opens a pair with
`posix_openpt`, sets the child's window size and termios, and spawns with `posix_spawn` using
`POSIX_SPAWN_SETSID` and a file action that opens the slave by path, which on Linux makes it the
controlling terminal. That avoids `fork` in a threaded GHC runtime entirely. (Checked on glibc 2.44:
the child is a session leader, the slave is its controlling tty, `/dev/tty` opens, and its process
group is the foreground group. musl has the flag since 1.1.17 and calls `setsid` before the file
actions, by reading its source; not yet run.) The C part is a small shim in `cbits/` behind
`Canopy.Ffi.Pty`, private by §2.6 rule 3. (The macOS equivalent needs `TIOCSCTTY` in a pre-exec hook
that `posix_spawn` lacks; D-deferred-5.)

**Canopy reads the child's termios from the master** with `tcgetattr` after every read and before
every submission — a single `ioctl`, and on Linux the master reports the slave's settings. That is how
canopy knows whether the child is running its own line editor (`ICANON` and `ECHO` off) or reading
cooked lines (§7.4) without guessing from output. Observed: a shell's `stty raw -echo` and back,
haskeline entering raw mode before `ghci>`, and GNU readline entering it before python's `>>>`, all
show up on the next read.

*Packet mode does not work for this* and is not used. `TIOCPKT` reports termios changes
(`TIOCPKT_IOCTL`) only while `EXTPROC` is set on the slave, and `EXTPROC` hands input processing to
the "external" side: with it set, the line discipline stopped echoing, never completed a cooked
`read`, and did not turn `^C` into SIGINT. Without `EXTPROC`, packet mode reported only flow-control
changes when the child went raw.

**Interrupts are bytes.** Ctrl-C while the child is busy writes the child's `VINTR` character to the
master; the line discipline delivers SIGINT to the child's foreground process group, which is what
every REPL expects and is language-agnostic. Ctrl-C while editing clears the input and never reaches
the child. Ctrl-D on an empty input sends `VEOF`.

### 6.3 The child as an effect

```haskell
data Child :: Effect where
  Spawn    :: Launch -> Size -> Child m ChildId
  Send     :: ChildId -> ByteString -> Child m ()
  Resize   :: ChildId -> Size -> Child m ()
  Signal   :: ChildId -> Signal -> Child m ()
  -- output, termios changes and exit arrive as Events through the queue, not as return values
```

Two interpreters: `runChildPty` (real) and `runChildScripted`, which plays a recorded or hand-written
script of output in response to input, for tests (§11.4).

### 6.4 Child lifecycle

```haskell
data ChildState
  = Starting  StartupProgress      -- running the profile's setup (§7.2); input is queued
  | Ready     PromptInfo           -- at a prompt; submissions go straight out
  | Busy      Submission BlockId   -- evaluating; type-ahead is queued and shown dimmed
  | Paging    Screen               -- child is full-screen or raw; host input passes through (§8.6)
  | Exited    ExitStatus           -- offer restart; transcript survives
```

Transitions are driven by framing events (§7.3), termios changes (§6.2) and process exit. Sending a
submission is a `Command` that `update` only emits from `Ready`; in other states it is queued in the
model. The constructors carry what each state needs, so "the current block while busy" is a field of
`Busy`, not a `Maybe` on the model that might be `Nothing` at the wrong time.

## 7. Language profiles

### 7.1 The profile type

Language-agnosticism lives here. A profile says how to drive one REPL; everything else in canopy is
generic.

```haskell
data Profile = Profile
  { name         :: ProfileName
  , detect       :: [Detector]            -- which project/file/command selects it
  , launch       :: Launch                -- argv, env, cwd; project-aware variants
  , setup        :: [SetupStep]           -- sent once after spawn (§7.2)
  , framing      :: Framing               -- how prompts and output are delimited (§7.3)
  , echo         :: EchoPolicy            -- (§7.4)
  , submit       :: SubmitStyle           -- how a multi-line input is sent (§7.5)
  , transport    :: Transport             -- Pty, for now (§7.6)
  , grammar      :: Maybe GrammarRef      -- tree-sitter (§9.1)
  , lsp          :: Maybe LspServer       -- (§9.2)
  , projection   :: Maybe Projection      -- transcript → shadow document (§9.2)
  , introspect   :: Introspection         -- REPL-native queries (§9.3)
  , modes        :: [InputMode]           -- Julia-style prompt modes (§8.9)
  , commands     :: [ProfileCommand]      -- profile-specific canopy commands (:core, :hoogle, …)
  , pastePrompts :: [PromptPattern]       -- prompts to strip from pasted transcripts (§8.5)
  }
```

**Built-in profiles are Haskell values** (`Canopy.Profile.Builtin.Ghci`, `.Python`, `.Node`, `.Julia`,
`.Utop`, `.Generic`), so they are type-checked with the program. **User profiles are TOML**, decoded
by a `toml-parser` codec into the same `Profile` at startup. Decoding is applicative validation — it
reports every error in the file at once, with locations — and it compiles everything that could fail
later: regexes, tree-sitter queries, LSP command existence (as a warning), keybindings. A profile that
loads cannot fail at use. A user profile may `extends = "python"` and override fields; the merge is a
typed partial record (`Profile Partial`, a higher-kinded-data variant) applied to a built-in.

### 7.2 Setup: making the child cooperate

Most of canopy's robustness comes from asking the child to emit **OSC 133 semantic-prompt marks**,
which libghostty-vt parses and reports as `SemanticPrompt` events (§4.5). Many REPLs let the prompt
string be set, and an escape sequence can be part of it:

| REPL | Setup | Status |
| :--- | :--- | :--- |
| ghci | `:set prompt "\ESC]133;A\a\ESC]133;B\aghci> "` and `:set prompt-cont` likewise; `:set -fdiagnostics-color=always` | Checked, GHC 9.12.4: ghci emits the marks raw before every prompt, and `:complete repl` and `:type` replies are cleanly between them |
| python | **A bootstrap, not the stock REPL**: `python3 -q -c '<boot>'` where `<boot>` sets `sys.modules["readline"] = None`, sets `sys.ps1`/`sys.ps2` with the marks (continuation as `133;A;k=s`), installs canopy's introspection helpers, and calls `code.interact(banner="", exitmsg="")` | Checked, CPython 3.14.7: the child stays cooked with echo, and marks frame each prompt. See below for why the stock REPL does not work |
| node | `repl.start({prompt})` via `-e` bootstrap, or `NODE_REPL_PROMPT`-equivalent options | Not yet checked |
| julia | `Base.active_repl` prompt functions; or OSC 133 hooks Julia already ships | Not yet checked |
| anything else | prompt regex fallback (§7.3) | — |

**Why python needs a bootstrap.** PyREPL (3.13+) redraws its prompt on every keystroke, and each
redraw re-emits `sys.ps1`, so the marks arrive many times per input and framing is meaningless.
`PYTHON_BASIC_REPL=1` replaces PyREPL with the basic REPL, but that still runs GNU readline, which
puts the terminal in raw mode; `-S` does not prevent it, and `-I` ignores `PYTHON_BASIC_REPL` and
brings PyREPL back. Setting `sys.modules["readline"] = None` from `-c` together with `-i` is too late,
because the interpreter imports readline before running `-c` when `-i` is given. The bootstrap avoids
`-i` altogether and runs its own `code.interact`, which reads through `input()` with no readline: the
child reads cooked lines. A bootstrap is also where canopy's introspection helpers (§9.3) are defined,
so it is the right shape for any language that allows one.

Setup steps are typed (`SetPrompt`, `SendLine`, `ExpectPrompt Timeout`) and run in the `Starting`
state; their echo and output are swallowed into a hidden startup block that is shown only if setup
fails. The child's own prompt text after the marks is kept and rendered by canopy as the prompt.

Like ghcitty, canopy then **refuses `:set prompt` (and the profile's equivalents) as user input**:
it would break framing. This is a profile-declared list of input patterns, checked before submit.

### 7.3 Framing

```haskell
data Framing
  = Osc133                         -- the child emits A/B/C/D, natively or via setup (§7.2)
  | PromptRegex Regex Regex        -- primary and continuation prompt, matched on child-terminal rows
  | Sentinel SentinelSpec          -- after each submission, also send a no-op that prints a nonce
```

OSC 133's marks, transcribed: `A` prompt start, `B` prompt end / input start, `C` input end / output
start, `D[;exit]` command finished. Most REPL prompts give only `A` and `B`; canopy derives `C` as
"first byte after the echoed submission" (§7.4) and `D` as the next `A`.

A **block** is then a pair of tracked grid refs (libghostty tracked refs survive scrolling and reflow)
into the child terminal: output start and output end. Blocks are the unit of everything in §8.

`Sentinel` is ghcitty's approach (fence each command with markers) and the fallback for REPLs whose
prompt cannot be set. `PromptRegex` is comint's and rlwrap's, the last resort; it is matched against
child-terminal *rows*, not bytes, so colour codes and cursor motion inside a prompt do not defeat it.

### 7.4 Echo

A child in cooked mode with `ECHO` set has its input echoed by the line discipline; a child running
its own line editor echoes (and redraws) its input itself. Canopy has already shown the input in its
own editor, so the echo is noise. `EchoPolicy`:

- `CookedChild`: the child reads cooked lines (python's bootstrap, §7.2), so the echo comes from the
  line discipline. Canopy clears `ECHO` on the child's termios before each submission and the echo
  never happens.
- `ChildEditorEchoes`: the child runs its own line editor in raw mode, which echoes and possibly
  redraws. Canopy hides the child-terminal rows from `B` to the first output, identified by comparing
  against the bytes it sent and by the editor's end-of-input sequence where the profile knows one.
  For ghci (haskeline) this is checked: the echoed input is followed by `ESC E` (NEL) and
  `ESC [?1l ESC >` (keypad mode off) before the output starts, which is an exact boundary.
  Note that haskeline enters raw mode even with `TERM=dumb` (checked), so there is no cooked ghci
  over a PTY; `TERM=dumb` only makes haskeline's echo simpler, which is still worth setting.

The policy is chosen per profile and confirmed at run time by the termios reads of §6.2: if a profile
says `CookedChild` but the child is raw at a prompt, canopy shows a one-time notice and falls back to
`ChildEditorEchoes`.

### 7.5 Submission

```haskell
data SubmitStyle
  = Lines                          -- send text with \r line endings
  | Bracketed                      -- wrap in bracketed paste if the child enabled mode 2004
  | Wrapped Text Text              -- e.g. ghci's ":{\n" … "\n:}"
  | BlankLineTerminated            -- python's basic REPL: compound statements need a trailing blank line
  | Custom (Text -> [ByteString])  -- built-in profiles only
```

Bracketed is chosen automatically whenever the child has enabled mode 2004 (read from the child
terminal's modes), encoded by libghostty's paste encoder so the child's own safety expectations hold.

### 7.6 Transport

`Transport` is `Pty` only, today. It exists as a type so that a later `JupyterKernel KernelSpec`
(ZeroMQ, structured execute/complete/inspect replies, rich MIME output) is a new constructor and new
interpreters, not a redesign. D-deferred-3.

| Auto-reload on source file change, with the result as a block | ghcitty, ghcid | `Canopy.Watch` + profile reload command |

### 8.5 Paste

- Bracketed paste from the host arrives as one `Paste` event and is inserted as text, never
  interpreted as keystrokes.
- **Pasted transcripts are cleaned**: if every non-blank line of a paste starts with one of the
  profile's `pastePrompts` (`>>> `, `... `, `ghci> `, `julia> `), the prompts are stripped and
  lines without them (output) are dropped, as Julia's REPL does. Offered, not forced: the original
  paste is one undo away.
- Pasting into a full-screen child goes through libghostty's paste safety check; a `Rejected` result
  (text that would execute) asks the user before sending (§4.7).

### 8.6 Passthrough

When the child switches to the alternate screen or turns on raw mode outside a prompt (a pager from
`help()`, a curses program, `:! vim`), canopy enters `Paging`: the host is switched to its alternate
screen, the child terminal's render state is mirrored to it cell for cell (a one-pane tmux), and host
input is decoded by tendril and *re-encoded* by libghostty's key and mouse encoders configured from
the child terminal's modes (kitty keyboard flags, mouse tracking modes the child requested). When
the child leaves, canopy restores its inline view. A configurable escape chord returns to canopy
without leaving the child mode.

### 8.7 Sessions

| Feature | From | Carried by |
| :--- | :--- | :--- |
| Auto-saved sessions, resumable with `--continue` (replays inputs) | ghcitty | transcript journal |
| Restore the *screen* of a session exactly, without re-running | — | `Ghostty.Effectful.Snapshot` |
| Named checkpoints; restore = restart + replay to the checkpoint | Ammonite | transcript |
| JSON-RPC mode on a socket: other tools submit inputs and read structured blocks | ghcitty's JSON mode | `Canopy.Serve` (milestone M7) |

A snapshot's byte format is outside libghostty-vt's ABI promise (§3.2), so a stored snapshot can stop
decoding after any library update. A session store keeps what restores the screen another way (the
transcript, replayed) and treats a snapshot that fails to decode as absent, never as an error.

### 8.8 History

History is an SQLite database (`sqlite-simple`) keyed by profile, with context per entry: working
directory, project root, session, timestamp, duration and whether the block errored — the model of
Atuin and McFly. Up-arrow does prefix search within the current profile; Ctrl-R opens a fuzzy search
popup that ranks by recency, same-project and success; multi-line entries are one entry. A history
browser (PyREPL's F2, ptpython's F3) lists entries without prompts and lets several be selected and
inserted.

### 8.9 Input modes

Julia's REPL switches mode by the first character typed at an empty prompt (`?` help, `;` shell,
`]` package manager), with a separate history and a different prompt per mode. Profiles declare
`InputMode`s with a trigger, prompt, grammar, and a submission transform (`?foo` → `:doc foo` for
ghci; `;ls` → run in the shell, output as a block, never sent to the child). Canopy provides two
generic modes for every profile: `;` shell and `:canopy` commands.

## 9. Syntax and semantics

### 9.1 tree-sitter

**Grammars are loaded at runtime**, which is what makes canopy language-agnostic without rebuilding:
shared objects in `$XDG_DATA_HOME/canopy/grammars/<lang>.so` exporting `tree_sitter_<lang>`, with
queries in `queries/<lang>/{highlights,injections,locals,indents,textobjects}.scm` — the layout Helix
uses, so its grammar and query collection can be pointed at directly. `canopy grammar fetch <lang>`
and `canopy grammar build <lang>` fetch a pinned grammar and compile it with the system C compiler.

Helix's queries are not quite standard: they use `; inherits: <lang>` directives and Helix's own
capture names. The grammar store implements `inherits` (a query file is the concatenation of the
files it inherits, then itself), and the theme table maps Helix's capture names. Predicates are
`tree-sitter-effectful`'s job (§5B.5); canopy compiles its own queries with `Strict` and third-party
collections with `IgnoreUnknown`.

**The binding is `tree-sitter-ffi` and `tree-sitter-effectful`** (§5A, §5B; D3). `hs-tree-sitter` was
the original choice and has the API canopy needs, but its last release (13.0.14.0, July 2025, no
commits since) vendors tree-sitter 0.24, whose maximum language ABI is 14; current tree-sitter is
0.27.1, and the grammars at the head of `tree-sitter-python`, `tree-sitter-haskell`,
`tree-sitter-javascript` and `tree-sitter-julia` are all ABI 15, which ABI-14 runtimes refuse to load.
Pinning every grammar to its 2024 tags to suit a binding is the wrong way round.

**Grammar pins are one table.** `canopy/grammars/pins.toml` names each built-in grammar's repository
and commit; `canopy grammar fetch` fetches exactly that commit, and the same commit's
`node-types.json` is committed beside it (`canopy/grammars/<lang>/node-types.json`) for
`deriveGrammar` (§5B.4). So the grammar a typed profile was compiled against and the one it loads are
the same by construction. A user who installs a different grammar by hand gets `bindGrammar`'s error,
naming what is missing, and that profile falls back to the dynamic, untyped features (highlighting
and completeness still work; the typed projection of §9.2 does not).

Canopy's modules over the binding:

| Module | Job |
| :--- | :--- |
| `Canopy.Syntax.GrammarStore` | Find grammars and queries in the Helix layout, `loadGrammar`, `bindGrammar` for known ones, resolve `inherits`, *compile every query*; any failure here is a startup error with the query's own line and column |
| `Canopy.Syntax.Grammars` | The `deriveGrammar` splices for the built-in profiles' grammars |
| `Canopy.Syntax.Edit` | The adapter from tendril's edits (grapheme-indexed, on a rope) to `splice`s (§5B.2): the one place the two unit systems meet |
| `.Highlight` | `TreeSitter.Highlight` over the changed ranges (`changedRanges`), with injections; captures decode to a closed `HighlightCapture` type and map to theme styles through a total table |
| `.Complete` | Completeness: an input is incomplete if the tree has an `ERROR` or `MISSING` node *at the end* of the input, or an unclosed bracket; an `ERROR` in the middle is a real syntax error and Enter submits (the child reports it). Profile rules can override (`:{` for ghci, trailing `\` for python) |
| `.Structure`, `.Indent` | Enclosing node ranges for selection and text objects; `indents.scm` with closed `IndentCapture`s |

**The current input's `Tree` lives in the model.** Each keystroke's edit is applied with `edit`, the
model keeps the previous tree for display until the new one arrives, and the parse is a `Command`
interpreted by the `Parse` effect with a budget of a few milliseconds; a parse that exceeds it is
`Aborted`, the previous highlighting stays, and the next idle tick retries without a deadline.
Because trees are values with pure reads (§5B.2), everything after the parse — highlighting,
completeness, structure — is part of the pure `update`.

Highlighting is synchronous and incremental (§5.5); **semantic highlighting** (LSP
`semanticTokens`) arrives asynchronously and overlays tree-sitter's spans when its revision matches.

Grammar and query compilation is the one place user-supplied code (queries) can fail, so it is done
once at startup, for every grammar every loaded profile names, and the test suite does the same for
every built-in profile against pinned grammars (§11.4).

### 9.2 LSP and the shadow document

A language server analyses files in a project. A REPL session is not a file, and the input is a
fragment that is usually not valid at top level. Canopy therefore maintains a **shadow document** per
session: a synthetic source file that the server is told about with `didOpen`/`didChange`.

```haskell
data Projection = Projection
  { path     :: ProjectRoot -> FilePath         -- where the shadow file claims to live
  , project  :: Transcript -> Input -> Shadow   -- pure
  }

data Shadow = Shadow
  { text      :: Rope
  , inputSpan :: SourceMap 'Input 'ShadowDoc    -- where the current input lives in the shadow
  }
```

`SourceMap from to` (§10.2) maps positions between the input editor and the shadow document in both
directions, and is the only way to convert them.

Per-language projections:

- **Python:** the accepted inputs in order, then the current input. Python's top level accepts
  everything a REPL does, so this is nearly the identity.
- **Haskell (ghci):** inputs are classified by tree-sitter: `import`s are hoisted to the module
  header; declarations go in the body in order (later shadowing earlier, so earlier same-named
  declarations are renamed); expressions become `canopy_it_N = <expr>`; statements `x <- e` become a
  declaration `x :: <type>; x = undefined` **whose type comes from ghci** (`:type x` after the
  block), so later inputs using `x` type-check (§9.3). The current input is projected the same way,
  and its span recorded.
- **Generic:** concatenation, or no projection (LSP disabled).

**The shadow file lives inside the project** (some servers, HLS among them, resolve project settings
from the file's location) as `.canopy/session-<id>.<ext>`, written to disk only if the server
requires it (a profile flag), and is excluded from VCS with a generated `.canopy/.gitignore`.

**The client** is canopy's own, typed by `lsp-types`:

- `Canopy.Lsp.Transport`: JSON-RPC over the server's stdio with `Content-Length` framing.
- `Canopy.Lsp.Client`: requests are `SMethod`-indexed (`lsp-types`'s singleton GADT), so a request's
  parameter and response types follow from its method at compile time.
- **Capabilities are evidence** (§10.3): after `initialize`, the negotiated server capabilities are
  turned into a record of `Maybe (Supports m)` tokens, and the request function requires the token.
  A request the server does not support cannot be written without first matching on its absence.
- Requests are cancelled (`$/cancelRequest`) when the revision they were for is superseded.
- Diagnostics are published for the whole shadow document; only those that map into the input span
  are shown, and diagnostics in earlier blocks are dropped (those blocks already ran).

### 9.3 REPL introspection

Runtime knowledge the server cannot have comes from the child itself, through **hidden queries**: a
profile's `Introspection` declares commands that canopy may send *when the child is `Ready` and the
user is not submitting*, with their output captured into a hidden block and parsed:

| Query | ghci | python |
| :--- | :--- | :--- |
| type of a name/expression | `:type e` | `type(e).__qualname__` (only for names; no evaluation of expressions) |
| completion | `:complete repl "<line>"` | `rlcompleter` / jedi `Interpreter` via a bootstrap function |
| documentation | `:doc n`, `:info n` | `pydoc.render_doc` |
| bindings list (binding explorer) | `:show bindings` | `globals()` keys and types |
| valid hole fits | evaluate with `_` and parse fits | — |

**Purity is declared.** Each query is marked as side-effect-free or not, and canopy never sends a
query that could evaluate user code without the profile saying it is safe (python's `type(e)` on an
arbitrary expression would run it; on a bare name it does not). This is how Node-style "eager
preview" is made safe: only for queries the profile proves pure — for ghci, `:type` of anything.

Introspection results are cached per (query, transcript length) and invalidated by every submission.

### 9.4 Merging the sources

`Canopy.Intel` merges completion candidates from LSP and the REPL: keyed by label, REPL candidates win
on type (they reflect runtime truth), LSP candidates win on documentation and edits. Ranking is
fuzzy-match score, then source (runtime bindings first, since a REPL user just made them), then
LSP's `sortText`. Hover and signature help prefer LSP and fall back to REPL introspection when the
server has no answer (a runtime-only binding) or no server is configured.

When the child is `Busy`, REPL queries are unavailable and the merge silently uses LSP only; when no
server is configured, it uses the REPL only; with neither, history-word completion (tendril's
default). A profile with nothing configured is rlwrap with a better editor, which is the floor.

## 10. Compile-time guarantees, collected

The brief is to prefer compile-time errors and minimise run-time ones. This section is the index of
how; each item is designed where it is cited.

### 10.1 Units and coordinate spaces in types

Seven different position systems meet in canopy: bytes (tree-sitter, VT), UTF-16 code units (LSP),
code points (Haskell `Text` APIs), grapheme clusters (cursor), display columns (rendering), child-
terminal cells, and host-terminal cells. Confusing two is the single most common bug in editors.

```haskell
newtype Offset (u :: Unit) = Offset Word
data Pos (space :: Space) (u :: Unit) = Pos { line :: Line space, col :: Offset u }
data Space = Input | ShadowDoc | ChildGrid | HostGrid
```

No `Num` instance on `Offset` (adding two offsets in different units cannot type-check); conversions
are functions of the rope that owns the text. `coerce` on these types is banned by an hlint rule
outside `Tendril.Text.Units` and `Canopy.Units`.

### 10.2 Source maps

`SourceMap from to` is the only way to move a position between spaces, and its two directions return
`Maybe` (a shadow position inside synthetic text has no input position). LSP edits and diagnostics
therefore cannot be applied to the input without passing through the map.

### 10.3 Capabilities as evidence

LSP server capabilities, host terminal capabilities (kitty keyboard, synchronized output, grapheme
mode, kitty graphics) and child terminal modes are each probed once and turned into tokens:

```haskell
data Supports (m :: Method f t) = Supports    -- constructor not exported
request :: Supports m -> SMethod m -> MessageParams m -> Eff es (Async (MessageResult m))
```

"Did we check that the server supports this?" becomes a type error instead of a review comment.

### 10.4 GADTs instead of tables

- `ghostty-effectful` keys (§4.4): the result type follows from the key; invalid keys are unrepresentable.
- tendril commands indexed by mode (§5.4).
- `lsp-types`'s `SMethod`, reused as is.
- Node kinds and fields of known grammars, generated from `node-types.json` (§5B.4); query captures
  decoded into closed types at query compile time (§5B.5); `EditedTree` distinct from `Tree`, so an
  edited, unparsed tree cannot be queried (§5B.2).
- `Event` and `Command` are closed sums handled by total functions; `-Wincomplete-patterns` under
  `-Werror` makes a new event an error everywhere it is not handled. An hlint rule rejects a wildcard
  `_ ->` alternative in `Canopy.App.Update` so the totality is real.

### 10.5 Parse, don't validate — at startup

Everything user-supplied (profiles, keybindings, themes, grammars, queries) is parsed into its typed
form at startup, with all errors reported together, and the program does not start if any fails.
After startup there is no stringly-typed configuration left. The runtime failures that remain are
external and are handled as values: the child exits (`Exited`), a server crashes (LSP disabled for the
session, with a notice, restart offered), a grammar's parse times out (highlighting falls back to
none for that revision). The deterministic runtime checks that remain are listed and each fails
immediately and loudly:

1. libghostty version mismatch at `runGhostty` (§4.7).
2. Use of the `Ghostty` or `Parse` effect from a second thread — statically prevented in canopy's
   loop, dynamically checked in the handlers for everyone else (§4.6, §5B.3).
3. `bindGrammar` against a grammar that lacks a kind the program was compiled against — at load,
   all names at once (§5B.4).
4. FFI `unsafe` calls re-entering Haskell — not checkable in general; prevented by review of the
   per-import comments in `ghostty-vt-ffi` (§3.3), and impossible in `tree-sitter-ffi`, where no
   callback is a Haskell function (§5A.3).

### 10.6 Unsafety audit

`unsafePerformIO`, `unsafeCoerce` and `reallyUnsafe*` are not in the prelude. Raw pointers exist only
in `Ghostty.FFI.**`, `Ghostty.Effectful.Internal.**`, `TreeSitter.FFI.**`, `TreeSitter.Internal.**` and
`Canopy.Ffi.**`, and exactly one module uses an unsafe primitive to present IO as pure:
`TreeSitter.Internal.Pure` (§5B.2), whose header states the argument for why its reads are pure. A
`grep` for `Foreign.Ptr|System.IO.Unsafe|Unsafe.Coerce` listing exactly those trees is the audit, as in
cassini.

### 10.7 Strictness

`StrictData` in every model module (`Tendril.**` T0–T4, `Canopy.App.Model`, `Canopy.Session.**`): a
long-running interactive program that accumulates thunks in its state leaks, and the leak is found
by users, not the compiler. Lazy fields are opted into with `~` where a structure is genuinely lazy.

### 11.1 Suites

| Suite | Package | What |

| `ghostty-vt-ffi-test` | ghostty-vt-ffi | Layout vs `ghostty_type_json`, version, enum coverage (§3.4) |
| `ghostty-effectful-test` | ghostty-effectful | Every typed key on a fresh terminal; event order; scoped-handle behaviour; formatter goldens |

| `canopy-test` | canopy | `update` as a pure function; profiles; projections; framing; source maps; scripted-child end to end |

tasty, tasty-quickcheck with a fixed seed in CI (cassini's `QUICKCHECK_SEED`), tasty-golden with the
cassini rule: **goldens are read before they are accepted**, and the commit says why the new output is
right. Every fixed bug adds a numbered regression case.

### 11.2 libghostty as an oracle

A complete terminal emulator available as a library is a test asset as much as a dependency:

- **Rendering goldens are screens, not byte streams.** Tendril's emitted VT is fed into a headless
  libghostty terminal of the same size, and the golden is the formatter's plain-text screen plus a
  style dump. A golden of bytes would fail on every harmless reordering of escapes; a golden of the
  resulting screen fails only when what the user sees changes.
- **Diff correctness, as a property**: for random pairs of grids, rendering A, then the diff A→B,
  produces the same ghostty screen as rendering B from scratch.
- **Input decoder roundtrip**: random key and mouse events under random keyboard-protocol modes are
  encoded by libghostty and decoded by tendril; the event must come back equal. A generated text
  key carries its unshifted character, as a platform's events do: ghostty's Kitty encoder finds a
  text key by it, and without one sends the press as its text and no release (found in M1.9).
- **Widths**: tendril's width tables agree with libghostty's for every codepoint, and for a corpus of
  grapheme clusters (emoji ZWJ sequences, flags, combining marks, Hangul).

### 11.3 Property tests of the editing model

Undo/redo inverse; cursor always on a grapheme boundary; every command preserves the rope's metric
invariants; source maps round-trip on every position that maps. Across the tendril–tree-sitter
adapter (`Canopy.Syntax.Edit`): a random sequence of tendril edits, applied as `splice`s and
re-parsed incrementally, gives the same tree as a fresh parse of the final buffer. (The same property
at the binding's own level is §5B.7's.)

### 11.4 The core as a pure function

`update :: Event -> Model -> (Model, [Command])` is tested by feeding event sequences and asserting on
the model and emitted commands. The scripted `Child` interpreter and a scripted LSP interpreter (a list
of expected requests and canned responses, failing on anything unexpected) make whole sessions
deterministic: "type `x = 1`, Enter, child prints prompt, type `x.`, completion arrives late with an old
revision" is a unit test. A tiny `canopy-fake-repl` test executable (an echo REPL that emits OSC 133)
exercises the real PTY path in CI without depending on any language being installed.

Built-in profiles are tested by compiling their grammars' queries against pinned grammar versions, and
their projections by golden shadow documents for transcripts.

### 11.5 End to end

`canopy-e2e` drives real REPLs through the real PTY with canopy's host side attached to a headless
libghostty terminal — a terminal inside a terminal inside a test — and asserts on the host screen.
Nightly only, against pinned versions recorded in the suite.

## 12. Performance

### 12.1 Budgets

| Path | Budget |
| :--- | :--- |
| Keystroke to frame on the host (typing in a 50-line input, with highlighting) | < 4 ms at p99 |
| Child output throughput (`cat` of a 100 MB file through the child) | ≥ 50% of raw `cat` into the same host |
| Idle CPU | ~0: no polling; everything is event-driven |
| Memory | Bounded by child scrollback (configurable; libghostty's compression is enabled after idle) |

### 12.2 How

- Child output is fed to libghostty in large chunks; render-state updates and frames are coalesced to
  the host's refresh (at most one frame per ~8 ms) and suppressed while the child holds synchronized
  output (`RenderHold`).
- Only dirty rows are copied out of libghostty (§4.3); only changed host cells are emitted (§5.6).
- Bulk output that scrolls past without the user looking is committed to host scrollback via the
  formatter's VT output in one write, not cell by cell.

### 12.3 Benchmarks

`tasty-bench`, cassini's arrangement: keystroke-to-frame on canned inputs, `feed` throughput,
incremental reparse and highlight of a one-character edit (in `tree-sitter-effectful`'s suite and,
end to end, in canopy's), decoder throughput. CI gates allocation (machine-independent) against a committed
baseline; time is reported, not gated. Baselines are regenerated deliberately with a commit saying why.

Each package's suite is `benchmark <package>-bench`, its modules `Bench.*` (as tests are `Test.*`,
§2.6), compiled `-O2 -with-rtsopts=-T` over a library at cabal's default optimization, as cassini's
are. Its baseline is `<package>/bench/baseline/ghc-<version>.csv`, from `cabal bench` with CI's
flags. `scripts/check-allocation.py` (cassini's) fails a benchmark that allocates more than 10%
*and* more than the slack over its baseline. CI passes a 4 KiB slack, not cassini's 1 KiB: the
streams whose per-byte work allocates nothing on the Haskell side allocate 4–8 KB per run, and
that figure moves by up to 1.3 KB between runs. A per-byte regression on a 1 MiB stream is
megabytes, and the per-write case still catches 16 bytes a write. Only Haskell allocation is
counted, so the gate guards the binding's work, not libghostty's.

**`feed` (M1.10)**, `ghostty-effectful-bench`: a fresh 80×24 terminal's life (`runGhostty`, open,
feed, free) on about 1 MiB of plain ASCII, SGR-coloured words, wide and combining text, and a REPL
transcript of OSC 133 blocks, plus plain text in 4 KiB writes and the life with nothing fed. First
figures (2026-11-07; GHC 9.12.4, one developer machine): open and close 24 µs; plain 1.4 ms;
unicode 5.9 ms; SGR 11.6 ms; 4 KiB writes 1.75 ms, about 900 bytes a write. The OSC 133 transcript
takes 224 ms and allocates 200 MB: about 3.2 µs and 2.9 KB for each of its 71,000 stops (§4.5),
linear in the stops and the same in 4 KiB writes. A REPL block has four marks, so this is not the
child-throughput budget's (§12.1) path, but the per-stop cost is the first place to look if a
stream of marks ever is.

It was looked at (2026-11-10, `perf` with DWARF call graphs): libghostty's parsing was about 16% of
the time. The rest was the runtime: the collector about 25%, and the mark callback about 22%,
because each call from C into Haskell makes a Haskell thread (its 1 KiB stack was half a stop's
allocation, as `+RTS -ki` showed). Pausing the thread for each stop's `safe` call was about 9%, and
the non-threaded scheduler's poll on each callback about 5%. With the mark copied in C instead (D18,
§4.5): 80–85 ms and 94 MB, about 1.3 KB a stop, against 160–170 ms and 161 MB; on the threaded
runtime 86 ms against 115–123. The two cursor reads a mark resolves now share one slot the terminal
keeps (`Internal.Keys.cursorAt`), not an `alloca` each, and a stop that drained nothing skips the
resolve and its `try` (2026-11-10): prompts 76 ms and 80 MB, about 1.1 KB a stop; plain text in
4 KiB writes 103 KB, from 171 KB. What is left is mostly the `safe` call and the events kept.

**Rendering**, the same suite's `Render` group: the same terminal life with a screen fed and a
render state opened, then one frame of every cell copied out (plain, SGR-coloured and wide/combining
screens), one frame's cursor and colours, and 24 frames of one new line each, the steady state of a
REPL. `no frame` is the life without the read. First figures (2026-11-10; GHC 9.12.4, one developer
machine): a full 80×24 frame takes 1.5–1.9 ms and allocates 1.6–1.9 KB a cell. Local helpers
inside a per-read or per-cell function are the cost to watch here. GHC binds each `Storable`
specialisation of a local polymorphic helper as a closure, which the function allocates on every
call. So the binding's readers are top level, and its small FFI read helpers are `INLINE`.

The other cost is the out-parameter. Each `alloca` is a pinned allocation, which costs more than
the read it serves, and a cell took ten. So a row's cell reads write into slots made once for the
row, one per type read (`Internal.Render.CellSlots`, through `outAt`, `optionalAtWith` and
`bytesAt`). Second figures (2026-11-10): a full frame takes 0.4–0.6 ms and allocates 400–600 bytes
a cell. The readers count as they go: summed lazily, the 24-frame case kept every frame's cells
alive to the end and measured the collector, at 100 ms where the reads take 12. Each new line
scrolls the screen, so all 24 of its frames are fully dirty and read every row.

## 14. Risks

### 14.1 libghostty-vt is unstable by its own declaration

Until 1.0 the header said the API would change, and the pin, the FFI quarantine, the layout test and
concept-shaped high-level types were the mitigations. They stay. Since 1.0 (M1.11) the C ABI is
stable across 1.x (§3.2): a minor release only adds, so a bump within 1.x should be small, and
exactly what the existing checks catch (a new enum value fails the layout test until named, a new
function fails the coverage check until bound or listed, a rewritten doc fails the safety check).
What remains of the risk:

- **The snapshot format** is outside the promise; §8.7 treats a snapshot that will not decode as
  absent.
- **Zig version coupling**: each 1.x may require a different Zig minor (1.0 requires 0.17), so a
  bump may move `ZIG_VERSION` in the build script.
- **The dynamic-link policy** is exact (D15); accepting any newer 1.x at run time is deferred
  (D-deferred-11), and would make `UnknownEnum` a reachable, documented error.
- **Deprecations do not fail `-Werror`**: a `GHOSTTY_DEPRECATED` function is a C warning in GHC's
  `capi` stubs, which GHC's `-Werror` does not cover. Consider `-optc-Werror=deprecated-declarations`
  in the common stanza (all seven `.cabal` files) at the next minor bump.

The open request to set default terminal modes in the C constructor (ghostty discussion #13474) is
the kind of addition to expect, and it affects only `newTerminal`.

### 14.3 Width disagreement with the host

If the host terminal's width for a cluster differs from tendril's, inline rendering corrupts the line.
Probing grapheme mode helps; a per-host override table and a "re-sync" command (full redraw) are the
fallback. Rendering inside Ghostty itself removes the risk, since tendril is tested against
libghostty's tables.

### 14.4 REPLs that will not be framed

Some REPLs cannot have their prompt set and print prompts indistinguishable from output. The regex
fallback degrades gracefully (blocks become approximate), and every feature that needs exact blocks
(fold, rewind) is disabled for profiles whose framing is `PromptRegex` — a property of the profile
type, so the UI cannot offer them.

### 14.5 Projection fidelity

Shadow documents will sometimes be wrong (a ghci statement form the classifier does not know), and the
server will report diagnostics on synthetic text. Diagnostics outside the input span are discarded,
and projections are golden-tested per construct, but the residual risk is spurious diagnostics in the
input; a per-session toggle hides them.
